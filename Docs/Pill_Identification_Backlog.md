## C0. [선행 필수] 실 식약처 낱알식별 데이터 적재 — 모든 항목의 전제

**현재 상태 (2026-05-16 갱신)**
- MariaDB: **mariadbd 가동 중**(정정: 앞서 "꺼짐" 은 오진 —
  mysqladmin TCP/비번 실패였을 뿐. 앱 계정 `medibridge_app`
  접속 가능).
- `pill_identification` = **64행** = 테스트 10 + 합성샘플 4 +
  **AIHub 유래 실 식약처 50종 적재 완료(2026-05-16)**.
  실 50종은 실 품목기준코드(item_seq)·실 약명·제조사·각인·
  색·모양·약효분류 보유(`(테스트)` 아님).
- `dur_interaction_cache` = 4행(시드) — DUR 전체는 여전히
  미적재.
- **여전히 미해결**: 전국 의약품 **수만 종 전체** 낱알식별·
  DUR 데이터. AIHub Validation 에 있던 50종만 실데이터화됨.

**왜 최우선 전제인가**
- C1~C5 전부 "DB 에 진짜 약이 있어야" 동작. 처방전에서
  "타이레놀" 을 정확히 읽어도(C1), DB 에 그 실제 약이 없으면
  매칭 0 → 무의미. R8 의 "매칭이 전부 (테스트) 약만" 도 동일
  원인.

**할 일**
- 식약처 의약품 낱알식별 데이터(공공데이터/OpenAPI 또는 식약처
  배포 CSV) 확보 → 기존 `MainServer/Scripts/import_pdma.py` 로
  `pill_identification`(+drug_overview/ingredient) 일괄 적재.
- DUR(병용금기/주의/효능군중복) 데이터도 별도 확보·적재
  (식별 후 안전성 체크용 — F-01 참조).
- 도구는 이미 있음. **데이터 확보(키 발급/다운로드)가 병목**.

**비용**: 데이터 확보 행정 + 적재·검증. 코드 신규 거의 없음.
**의존**: 식약처 공공데이터 접근. **이게 안 되면 C1~C5 전부 보류.**

적재 시도 → **FK 위반으로 차단**(부분삽입 0, 오염 없음):

- → 데이터는 받았으나 **현 스키마로 직접 적재 불가**. 억지
  적재(FK 해제 + 고아행 54만)는 비기능·DB오염이라 **안 함**.

## C1. 처방전/약봉투 OCR 연동 — 검색공간 선축소 (최우선 후보)

**아이디어**: 알약 촬영 *전에* 약봉투/처방전을 먼저 촬영 →
인쇄 텍스트 OCR 로 약품명 3~5개 리스트 확보 → 이후 알약
DB 검색을 5만 종이 아니라 **그 5개로 한정**.

**왜 강력한가 (우리 데이터와 직결)**
- R8~R10: 이미지 특징만으론 미학습 약 일반화 실패. 그러나
  후보가 5개로 좁혀지면 **각인 없는 파란 연질캡슐도 색·모양
  만으로 거의 100% 특정** 가능 (5만→5 면 약한 특징도 충분).
- 인쇄 처방전/약봉투 텍스트는 PaddleOCR 가 **잘하는 도메인**
  (음각 알약 각인과 정반대 — 깨끗한 인쇄 한글/영문). 즉
  실패하던 OCR 을 *잘되는 OCR 문제*로 바꿈.

**기존 아키텍처 적합도 — 높음**
- 신규 흐름: 처방전 촬영 → OCR → 약품명 리스트 → 기존
  `POST /v1/pill/onboarding/normalize`(이미 drug_name LIKE
  매칭 구현됨) 재사용 → 그 결과 item_code 집합을
  `/v1/pill/identify` 후보 제약조건으로 전달.
- MainServer Pill.cpp 매칭 SQL 에 `WHERE item_code IN (...)`
  한 줄 추가 수준.

**비용·의존성**
- 클라 UX: "처방전 먼저 촬영" 단계 추가(선택적 — 없으면 기존
  전체검색 fallback).
- 인쇄 OCR: PaddleOCR(korean) 그대로 사용 가능(별도 학습
  불필요로 추정 — 인쇄체라 사전학습으로 충분할 가능성 높음,
  소규모 검증 필요).
- 처방전 레이아웃 다양성(병원·약국별) → 약품명 추출 robust성
  검증 필요(후속 실험 C1-R).

**예상 효과(추정)**: 식별 정확도 최대 레버. 이미지 모델
한계를 우회하므로 R8 의 "전체 5000종 재학습" 보다 비용 대비
효과가 클 것으로 생각된다(미검증).

## C2. 다빈도 유통 의약품 Top-N 가중치 — 스코어 하이퍼파라미터

**아이디어**: 5만 종 중 실제 환자 처방 대부분은 상위
1,000~2,000종. 매칭 스코어에 **유통빈도 가중치**를 곱해 희귀
의약품을 후순위로.

**기존 아키텍처 적합도 — 매우 높음**
- MainServer Pill.cpp 의 가중 스코어 매칭(각인5+색2+모양2)에
  `+ freq_weight(item_code)` 항 추가. 기존 쿼리 한 줄 확장.

**의존성**
- **다빈도 처방 데이터 필요** — 건강보험심사평가원(심평원)
  '다빈도 상병/약효' 또는 의약품 처방·조제 통계(공개 데이터)
  확보 → item_code↔처방빈도 매핑 테이블 적재.
- 데이터 없으면 가중치 미적용(중립) fallback.

**비용**: 데이터 확보·정제만 되면 구현 매우 저렴(스코어 항
1개). 단독으론 보조, C1 과 결합 시 시너지.

**리스크(정직)**: 빈도 가중은 희귀약을 가진 환자에게 불리
(오분류 위험). '후순위'일 뿐 '제외'는 아니어야 하고, 가중
강도는 튜닝·검증 대상.

## C3. (R8 도출) 각인 OCR — 전체 ~5,000종 fine-tune

AIHub Training 스플릿(전체 ~5,000종) 확보 → 기구축 파이프라인

## C4. (R8·R10 도출) VLM 기반 각인/특징 리더

작은 OCR 대신 비전언어모델로 각인·색·모양 동시 판독.
약별 학습 불필요·미학습 약 일반화(클로드가 KG 를 학습없이
읽음). 트레이드오프: 지연·비용·오프라인·의료 프라이버시 —
소규모 실측 필요(R 후보).

## C5. (R9·R10 도출) 색·모양도 학습 기반 분류기로

OpenCV 규칙(색 ~28%·모양 ~50%, R9) 한계 → AIHub
color_class/drug_shape 라벨로 경량 분류 CNN 학습 검토.
데이터·라벨 이미 보유(R9 매핑표 활용).

## C6. (R9 도출·방법론) 고정 벤치마크 + 검증 GT 의무화

모든 비전 평가는 ① 고정 사진/데이터셋 ② 공식 사람라벨
(또는 사용자 검증 GT) 기준으로만. "최신 사진 매번" 금지 —
"매번 결과 바뀜"의 근본 원인이었음.

### 우선순위 제언 (추정 — 결정은 사용자)
0. **C0(실 낱알식별 데이터 적재)** — 절대 선행. 이거 없으면
   C1~C5 전부 의미 없음. 식약처 데이터 확보가 1순위 행정과제.
1. **C1(처방전 OCR)** — 효과 최대·아키텍처 적합·OCR 강점
   도메인. 가장 먼저 소규모 PoC 가치. (단 C0 전제)
