# 1. 문서 개요

## 1.1 목적

본 문서는 **메디브릿지(MediBridge) 플랫폼**의 1차 개발 계획을 정의한다. 메디브릿지는 알약 식별·복약 이력·증상 기록·헬스케어 데이터 연동·통합 보고서 등 6개 모듈로 구성되는 복약·건강 통합 케어 플랫폼이며, 본 프로젝트의 MVP는 그중 **모듈 1(알약 식별 + 안전 점검)** 과 **모듈 2(복약 이력 관리 — 핵심 기능)**, **모듈 5(통합 보고서)**, **모듈 6(사용자 인증)** 을 우선 구현한다. 프로젝트 범위·개발 기간·자원·리스크·운영 규약을 정리하여 팀의 개발 기준선이 되도록 한다. 일자별 상세 스케줄은 별도 「개발스케줄」 문서에서 다룬다.

## 1.2 적용 범위

- MVP(본 프로젝트 범위)에 한정한 개발 계획

- 사업화·확장 단계는 본 계획서 범위 외, 추후 검토

# 2. 프로젝트 개요

## 2.1 프로젝트 목표

- 머신비전 통합 시스템 구축 (서버·TCP/IP·DB·Qt/C++ GUI·AI 모델 모두 활용)
- 취업 포트폴리오용 — 개발부터 배포까지 전 과정 경험 확보
- 사회적 가치 — 고령층 복약 혼동 예방 + 다제 복용자 안전성 점검 보조

## 2.2 한 줄 컨셉

**메디브릿지** — 알약 식별·복약 이력·증상·헬스케어 데이터를 통합해 의사 상담용 보고서로 연결하는 **복약·건강 통합 케어 플랫폼**.

본 프로젝트(MVP) 범위는 그중 **모듈 1: 알약 식별 + 안전 점검** 을 중심으로, 모듈 2(복약 이력), 모듈 5(통합 보고서), 모듈 6(인증)을 함께 구현한다. 알약 사진(여러 알 동시 촬영 가능)과 음성 질문(폰 온디바이스 STT로 변환된 텍스트)을 입력으로 받아 약을 식별하고, 식약처 DUR과 결합해 병용금기·중복 처방 위험을 점검하는 한국 식약처 데이터 기반의 국내 알약 식별 도구가 모듈 1의 핵심이다.

## 2.3 타깃 사용자

- 주 타깃: 고령층 — 음성 인터페이스 기반의 쉬운 접근성, 복약 혼동 예방
- 보조 타깃: 청·장년층 — 다제 복용 자가 관리, 사전 등록 기반 체계적 복약 관리
- 유니버설 디자인 사상은 적용하되, 핵심 시나리오·시장 근거는 고령층 중심으로 유지

## 2.4 시장성 (요약)

| 지표 | 내용 |
| --- | --- |
| 글로벌 의약품 정보 앱 시장 (직접 진입) | 2025년 14.7억 달러 → 2035년 35.5억 달러 (CAGR 9.2%) |
| 글로벌 의약품 관리 시장 (상위 우산) | 2023년 30억 달러 → 2033년 82억 달러 (CAGR 10.6%) |

| 국내 약국 사고 통계 | 약국 사고 86.1%가 처방 단계, 복약 단계 사고 중 65세 이상이 61.7% (대한약사회 환자안전약물관리원 2025) |
| 타깃 시장 | B2C(가정 복약관리), B2B(약국 복약지도 보조, 요양원·요양병원 복약관리) |

## 2.5 메디브릿지 플랫폼 전체 모듈 구조

메디브릿지는 6개 모듈로 구성되는 통합 플랫폼이다. 본 프로젝트(MVP)는 모듈 1·2·5·6을 우선 구현하고, 모듈 3·4 및 확장 모듈은 추후 단계에서 진행한다.

| # | 모듈 | 본 프로젝트 (MVP) | 비고 |
| --- | --- | --- | --- |
| **1** | **알약 식별 + 안전 점검** | ✅ **핵심** | YOLO26·PaddleOCR·OpenCV·LLM·식약처 DUR. 사전 등록 약 풀 기반. 본 프로젝트의 무게중심 |
| **2** | **복약 이력 관리** | ✅ 포함 | 복용 시각·약·개수·메모. 일자별·약별 조회 |
| **3** | 증상 / 부작용 기록 | ⚠️ 확장 | 사용자가 느낀 증상을 텍스트·음성으로 기록. 복용 시각과 매칭하여 의료진 인과 추정 보조 |
| **4** | 헬스케어 데이터 연동 | ⚠️ 확장 | 핸드폰 심박·걸음·수면·활동량 (Health Connect / HealthKit) |
| **5** | **통합 보고서** | ✅ 포함 | 의사 상담용 인쇄/PDF. MVP는 약 정보 + 복약 이력 + 식약처 부작용 인용. 확장에서 모듈 3·4 데이터 추가 |
| **6** | **사용자 계정 / 인증** | ✅ 포함 (공통 인프라) | 회원가입·로그인. 모듈 간 사용자 데이터 통합 |

### 확장 로드맵 (본 프로젝트 범위 외)

- **음성 → 복약 이력 자동 기록** — "타이레놀 2알 먹었어" 발화 → 폰 STT → LLM 추출(약명·개수·시각) → 복약 이력 DB 자동 저장
- **음성 → 복약 이력 자연어 조회** — "어제 먹은 약 뭐야?" → DB 조회 + 정해진 템플릿 출력
- **복약 알림·리마인더** — 시각 알람, 미복용 알림
- **가족·간병인 공유** — 보호자가 환자 복약 상태 모니터링
- **약사·의료진 연계** — 보고서 전자 전송, 표준 양식
- **자유 대화 컨텍스트 유지** (멀티턴 챗봇) — 의료 안내 영역 진입 위험 통제와 함께 별도 설계 필요

# 3. 개발 범위

## 3.1 MVP 범위 vs 확장 범위

본 프로젝트는 메디브릿지 플랫폼의 **모듈 1·2·5·6**을 MVP로 구현한다. 모듈 3·4와 추가 확장은 본 계획서 범위 외이다.

### 3.1.1 모듈 1 — 알약 식별 + 안전 점검 (MVP 핵심)

| 항목 | MVP (본 프로젝트) | 확장 (범위 외 / 추후 검토) |
| --- | --- | --- |
| 대상 약 범위 | 국내 약 (식약처 OpenAPI 등재, 약 24,633품목) | 해외 약 (별도 설계 필요) |
| 카메라 | 안드로이드 S24 폰 카메라 (USB 직결 또는 WiFi 전송) | Basler pylon + Ring Light |
| **STT** | **폰 온디바이스 STT (Galaxy AI / Android `SpeechRecognizer`)** | **추론 PC Whisper fallback** |
| 알약 촬영 | 단면 촬영 + 사용자 가이드(앞뒷면 뒤집기) | 거울 / 지그재그 거치 (양면 촬영 대안) |
| DUR 위험 카테고리 | ① 병용금기 | ②~⑧ (특정연령대금기·임부금기·용량주의·투여기간주의·노인주의·효능군중복·서방정분할) |
| 등록 방법 | 음성 인식(폰 STT) + 직접 입력 | + 단일 촬영 등록 |
| 등록 약 관리 | 추가 / 삭제(soft delete) / 전체 리셋(수동) | + 정확도 모니터링·정리 자동화 |
| 입력 채널 | 카메라 + 음성 질문 (둘 중 하나 또는 결합) | — |
| LLM·RAG 활용 | 등록 + 의도 분류 + 비의료 일반 안내 | 등록 LLM·RAG 정교화 (e약은요 자연어 요약 확대) |

## 3.2 본 프로젝트 범위 외 — 명시적 제외

**플랫폼 차원 (확장 모듈)**

- **모듈 3 (증상 / 부작용 기록)** — 본 MVP에 포함하지 않음. 기능 자체는 단순하나 사용자 시나리오·UX 설계 시간 확보 필요
- **모듈 4 (헬스케어 데이터 연동)** — 핸드폰 OS별 권한·SDK 연동(Health Connect, Apple HealthKit) 부담으로 확장 단계로 이동
- **음성 → 복약 이력 자동 기록 / 자연어 조회** — 모듈 2의 확장 기능. STT·LLM은 이미 보유하지만, 정확도 검증·UX 안정화 시간 확보를 위해 확장으로 이동
- **복약 알림·리마인더, 가족·간병인 공유, 약사·의료진 연계** — 사업화 단계의 확장 모듈

**모듈 1 차원 (알약 식별 한정)**

- 동일 성분 시간차 누적 카운팅(약물동력학 기반 자동 차단) — 의료적 판단 영역에 가까워 범위 외
- 정식 의료기기 인증 (식약처 의료기기 허가, ISO 13485, GMP 등) — 사업화 단계
- 병원·약국 협업 안전성 검증, 유관 단체 자문, 긴급 연결 라인 — 사업화 단계

# 4. 시스템 아키텍처 요약

> 본 장은 메디브릿지 플랫폼이 **물리적/논리적**으로 어떻게 구성되는지를 다룬다. MVP에서 구현하는 모듈 1·2·5·6은 모두 동일한 PC 4대 분리 구조 위에 얹는다. 향후 확장 모듈(3·4 등)이 추가되더라도 운용 서버 PC에 모듈을 추가하는 형태로 확장 가능한 구조이다.

## 4.1 PC 4대 분리 구성 + 폰 입력 디바이스

| PC | 역할 | 주요 구성 |
| --- | --- | --- |
| ① GUI PC | 사용자 클라이언트 | Qt6 + C++ + QML, **폰(S24) 입력 수신**(USB/WiFi: 이미지 + STT 텍스트), 마이크는 폰이 처리, TTS 출력 |
| ② 운용 서버 PC | 비즈니스 로직 + DB | FastAPI, MariaDB(약 풀 + 식약처 4종 캐시), 위험 템플릿 |
| ③ 추론 PC | AI 추론 (GPU) | YOLO26·PaddleOCR·OpenCV, **(확장) Whisper STT fallback**, LLM 의도 분류기·등록 보조 |
| ④ 학습 서버 | 별도, 운용 중 비활성 | 데이터 수집·모델 학습·검증 → 추론 PC로 모델 배포(SCP) |
| **(입력) 안드로이드 S24** | 카메라 + 마이크 + 온디바이스 STT | Galaxy AI / `SpeechRecognizer`로 음성→텍스트, 이미지·텍스트를 GUI PC에 전달 |

> ⚠ 제한된 개발 기간을 고려해 초기에는 단일 PC 또는 2대 PC 환경에서 시작 → 통합 단계에서 4대로 분리. 부족 시 한 PC에 컨테이너/프로세스로 논리적 분리를 유지한다.

## 4.2 통신 구간

| # | 구간 | 방식 | 비고 |
| --- | --- | --- | --- |
| 1 | GUI PC ↔ 운용 서버 | TCP/IP (REST API on HTTP) + 미디어/텍스트 별도 엔드포인트 | 일반 API REST, 이미지·STT 텍스트 별도 엔드포인트 |
| 2 | 운용 서버 ↔ 추론 PC | TCP/IP (REST API on HTTP) | 추론 요청·응답 (REST 단일화) |
| 3 | **폰(S24) ↔ GUI PC** | **USB 또는 WiFi** | MVP: 안드로이드 S24 카메라+마이크+STT / 확장: pylon SDK |
| 4 | 운용 서버 ↔ 식약처 OpenAPI | HTTPS | e약은요 캐시 미스 시에만 (낱알식별·DUR은 일괄 적재로 운용 중 호출 없음) |
| 5 | 학습 서버 → 추론 PC | SCP / 파일 전송 | 모델 배포 시에만 |

## 4.3 핵심 설계 결정

- LLM·RAG는 등록 + 의도 분류 + 비의료 일반 안내에 한정. 의료 안내 영역(DUR 위험 안내)에는 미사용 — 환각·왜곡 차단
- 위험 안내는 식약처 DUR 데이터 → 정해진 템플릿으로만 출력 (단정 문구 금지)
- **식약처 데이터 적재 전략 (단순화)** — 낱알식별·DUR 품목·DUR 성분은 식약처가 제공하는 **CSV/EXCEL 파일 일괄 다운로드** 또는 **스마트싱크(MariaDB 자동 동기화 도구)** 로 초기 적재 + 주기적 갱신. e약은요(효능·복용법)는 사용자가 등록·조회한 약만 lazy 캐싱(만료 정책 없음). **TTL/ETag 정책 미사용**
- **(v2.0 신규) 음성 입력 — 폰 온디바이스 STT 채택** — 안드로이드 S24의 내장 AI(Galaxy AI / Android `SpeechRecognizer`)로 클라이언트 측에서 음성→텍스트 변환 후 송신. 운용 서버·추론 PC 구간에 음성 바이너리가 흐르지 않아 대역폭 절감 + 개인정보 노출 위험 감소. 추론 PC Whisper STT는 확장 fallback
- **사용자 인증** — 회원가입·로그인으로 사용자별 약 풀과 복약 이력을 분리 관리. 비밀번호는 해시(bcrypt 등) 저장
- **복약 이력 기록** — 복용 시각(분 단위), 약 이름·개수, 메모, 사용자별 식별 결과·DUR 위험 검출 결과를 영속 저장. 의사 상담용 보고서 출력 기능 제공
- 프롬프트 인젝션 방어 다층 — 입력 검증 + 시스템 프롬프트 락(JSON 스키마) + 영역 분리 + 로그 감시
- Arduino 미사용 — 회전 거치대는 가격·공간 부담 대비 효용 낮음 (단면 촬영 + 사용자 가이드로 대체)

# 5. 기능 영역 분리 (담당자 매핑 없음)

> 본 절은 시스템을 **기능 단위로 분리**한 분류이다. 팀원과 영역 간의 1:1 매핑을 두지 않는다. 모든 팀원이 AI 모델링·학습·평가 작업에 공동 참여하며, 각 영역은 팀 협의로 1차 책임자만 두고 작업은 협업 중심으로 진행한다.

## 5.1 기능 영역 구분

| 영역 | 담당 영역 | 주요 업무 |
| --- | --- | --- |
| **영역 A** | AI 추론 / Vision / Speech | YOLO26 알약 검출, PaddleOCR 각인 인식 + fine-tuning, OpenCV 색·모양·크기 분석, **(확장 fallback) Whisper STT**, LLM 의도 분류기 (Stage 0.5), LLM·RAG 등록·일반 안내 보조, 학습 서버 ↔ 추론 PC 모델 배포 절차 정립 |
| **영역 B** | 운용 서버 / DB / 통신 / 캐싱 | FastAPI 백엔드, MariaDB 스키마(사용자 계정 + 사용자별 약 풀 + 복약 이력 + 식약처 데이터), 식약처 데이터 일괄 적재(CSV/스마트싱크) + e약은요 lazy 캐싱, **모듈 1**(DUR 위험 검출 + 정해진 템플릿 출력), **모듈 2**(복약 이력 기록·조회 API), **모듈 5**(통합 보고서 생성), **모듈 6**(회원가입·로그인·세션/토큰 관리), TCP/IP·REST API 통신, 프롬프트 인젝션 방어, 자원 모니터링·자동 재연결·로깅 |
| **영역 C** | GUI / 클라이언트 / UX | Qt6 + C++ + QML GUI(기능 단위 모듈 분리), **모듈 1**(폰(S24) 입력 수신: 이미지+STT 텍스트, 결과 표시(신뢰도 분기), 등록·관리 UI, 능동/대화형 가이드, TTS 클라이언트), **모듈 2**(복약 이력 입력·조회 화면), **모듈 5**(보고서 출력 화면), **모듈 6**(회원가입·로그인 화면), 사용자 환경별 입력 옵션(클릭/음성) |

## 5.2 공동 진행 영역 (전원 참여)

- **AI 모델링·학습·평가** — 데이터 준비, 학습 파이프라인 운영, 모델 평가는 팀 전원이 공동 진행
- **데이터셋 수집·정리** — AI Hub 5,000종 + 식약처 데이터 정제는 공동 책임
- **인터페이스 합의** — 영역 간 인터페이스(REST API, TCP/IP, DB 스키마)는 팀 협의로 확정
- **통합 테스트** — 통합 단계는 모두 참여
- **교수 컨펌** — 주제·자원·아두이노 미사용 결정 컨펌은 팀 전체로 진행
- **문서 작성** — 1차 제출 문서(개발계획서·개발스케줄·요구사항 분석서·순서도·DB ERD·통신 프로토콜·디자인 목업)는 공동 작성 후 팀장(김윤식)이 일괄 제출

## 5.3 영역 간 인터페이스 합의 일정 (Phase 1 내)

개발 초기 단계에 다음 인터페이스를 팀 합의로 확정하고, 변경 시 즉시 동기화한다.

- [A ↔ B] 추론 PC REST API 명세 (엔드포인트·요청/응답 스키마)
- [B ↔ C] GUI ↔ 운용 서버 TCP/IP 메시지 포맷 (이미지·**STT 텍스트**·요청·응답)
- [B ↔ MariaDB] 사용자 계정 + 사용자별 약 풀 + **복약 이력** + 식약처 데이터 스키마
- [B ↔ 식약처] 데이터 적재 절차 (CSV/스마트싱크 일괄 적재 + 갱신 주기) + e약은요 lazy 캐싱 정책
- [인증] 회원가입·로그인 흐름, 세션/토큰 방식 (예: JWT)
- **[폰 ↔ C] 폰(S24) ↔ GUI PC 어댑터 명세** — USB/WiFi 채널, 이미지 포맷, STT 텍스트 포맷, 페어링 절차
