# 특이사항

- **외부 지식 데이터(External Knowledge Sources)는 필요한 곳에만** — 단순 lookup 으로 풀리는 문제에 RAG 구조를 끼워 맞추지 않음
- **개발 ~ 배포 전 과정 경험** 가능한 범위로 한정

> **용어 메모**: 본 프로젝트의 외부 지식 데이터(식약처 데이터 4종)는 **Rule-based 조회 우선**, **비의료 영역(약 정보 등록·일반 안내) 한정 RAG 활용**, **의료 안내 영역(DUR 위험 안내·진단성 응답)에는 LLM·RAG 모두 미사용**. 식별·DUR 핵심 데이터(낱알식별·DUR 품목·DUR 성분)는 식약처 CSV/EXCEL 또는 스마트싱크로 일괄 적재, e약은요(효능·복용법)는 사용자 요청 시점에 lazy 캐싱(만료 정책 없음).

## 1. 한 줄 컨셉

**메디브릿지(MediBridge)** — 알약 식별·복약 이력·증상·헬스케어 데이터를 통합해 의사 상담용 보고서로 연결하는 **복약·건강 통합 케어 플랫폼**.

본 프로젝트(MVP) 범위는 **모듈 1·2·5·6** (모듈 1 = 알약 식별 + 안전 점검 중심). 알약 사진(여러 알 동시 촬영 가능)과 음성 질문(폰 온디바이스 STT 결과 텍스트)으로 약을 식별하고, 식약처 DUR과 결합해 병용금기·중복 처방 위험을 점검한다.

> 모듈별 상세 구조는 「[기획서 v3 §1.1](기획서_ver3.md)」 참조.

## 5. 활용 시나리오

### 5.1 [주 타깃] 노인 복약 혼동 예방
노인이 약을 헷갈려 복용하는 사고 발생. 사전 등록된 약 풀로 식별 정확도를 높이고, DUR로 위험 자동 검출. 음성 인터페이스로 키보드 조작 부담 최소화 (출처: 팀원 지인의 요양원 근무 경력 청취).

### 5.2 [주 타깃] 요양원·병원 투약 전 최종 체크
다수 환자의 알약을 투약하기 전 일괄 검수 — 간호사·요양보호사의 반복 작업 자동화 (확장 단계).

### 5.3 [주 타깃] 일반의약품 자가 구매 시 안내 누락 보완
동일 약국에서 진통제 + 감기약을 함께 사면 약사가 동일 성분 중복(아세트아미노펜 등)을 안내. 그러나 다른 약국·다른 시점 별도 구매 시 안내 누락 — 사용자가 모든 약을 등록해두면 시스템이 DUR로 위험 자동 검출.

### 5.4 [보조 타깃] 청·장년층의 체계적 복약 관리
처방약·일반의약품·영양제 등 다양한 약 동시 복용 시 중복 성분·상호작용 인지 어려움 — 사전 등록 후 새로운 약 추가 시 자동 DUR 점검, 음성 질문으로 신속한 정보 확인 (예: "이 약 공복에 먹어도 돼?").

### 5.5 [모듈 5 — MVP] 의사 상담 시 통합 보고서 출력
사용자가 복용한 약의 종류·개수·이름·복용 시각을 보고서로 출력해 의사·약사에게 제출. 약별 부작용 주요 증상은 식약처 e약은요 데이터에서 인용. 인쇄 또는 PDF 형태.

### 5.6 [확장] 음성으로 복약 이력 기록
"타이레놀 2알 먹었어" 발화 → 폰 STT → LLM 추출 → 복약 이력 DB 자동 저장.

### 5.7 [확장] 헬스케어 데이터 통합 보고서
핸드폰 건강 데이터(심박수·걸음수·수면)를 복약 이력과 함께 통합 보고서에 표기.

## 6. 핵심 설계 원칙 — 한계와 대응 (모듈 1)

알약 5,000종 중 정확한 1:1 식별은 본질적으로 어려움 (외형 유사성 + 각인의 미세함). 따라서 **사전 등록 + 다층 안전 메커니즘 + 2단계 추론**으로 설계.

### 6.1 사전 등록 (Onboarding)
식별 범위를 **5,000종 → 등록된 N종**으로 좁혀 정확도를 본질적으로 해결:

- **음성 인식 등록**: 폰 온디바이스 STT로 약명 입력 → 식약처 DB 검색(RAG) → 사용자 확인. LLM이 동명·동성분 약 후보를 **분기 질문으로 정리**(예: "예전에 드셨던 OO약인가요? 최근 드시는 OO약인가요?"). **다회 round-trip 허용** (max_rounds·token·rate 제한). API: [PillApi v0.3 `POST /v1/pill/onboarding/normalize`](Api/PillApi.md), 흐름: [시스템_연결구조 v2.2 §2.8](시스템_연결구조_ver2.md)
- **직접 입력 등록**: 약명·각인 입력 → 식약처 DB 검색
- **단일 촬영 등록**: 알약 한 알 정밀 촬영 → Top-N 후보 → 사용자 선택 (확장 범위)
- **확인 절차**: 음성 응답 또는 화면 클릭 (사용자 환경 선택)
- **등록 약 관리**: 추가 / 삭제(soft delete) / **전체 리셋(사용자 수동 트리거만)** — 분류 카테고리 누적 시 정확도 저하 방지

### 6.2 일상 사용 흐름 (3단계)

- **Stage 0.5 (음성 입력 시에만)**: LLM 의도 분류기 → 카테고리 분류(약 식별/위험 점검/일반 정보 확인/등록 요청/복약 이력 조회/보고서 출력). 응답 생성 X. 정보 부족 시 능동/대화형 가이드 (TTS).
- **Stage 1**: 검출 → OCR(각인) + 색·모양 분석 → 등록된 N종 풀에서 매칭
- **Stage 2**: 식별된 약 조합을 DUR API로 조회 → 위험 자동 검출 (정해진 템플릿으로 출력)

### 6.3 다층 안전 메커니즘

- **사전 등록 효과**: 식별 범위 5,000종 → 사용자 N종 축소 — AI Hub 베이스라인 Top-5 10%의 한계 우회
- **하드웨어 보강**: 안드로이드 S24 폰(MVP) — 미세 각인 인식. 확장 시 pylon 산업 카메라 + Ring Light로 추가 보강
- **신뢰도 단계 메시지**: 95%↑ 표시형 / 70~95% 후보 비교형 / 70%↓ 식별 불가 안내
- **표현 톤**: 모든 결과를 "추정" + "식약처 DUR 인용" + "약사·의사 상담 권유" 톤으로 통일. **단정 문구("복용 가능합니다 / 불가합니다") 사용 금지**. 안전 케이스도 단정 X — "DUR 등록 확인되지 않음 + 약사·의사 상담 권유"
- **LLM·RAG 활용 영역 제한**:
    - ✅ 약 정보 등록(Onboarding) — RAG 허용 (폰 STT 결과 약명 추출·정규화, 모호한 약명 후보 추천, 동명·동성분 분기 질문 생성, 등록 확인 단계 e약은요 자연어 요약). **벡터 DB: ChromaDB** (LLM PC 10.10.10.128 동거)
    - ✅ 일상 사용 의도 분류기 (Stage 0.5) — 분류만, 응답 생성 X
    - ✅ 비의료 일반 안내 보조 — RAG 허용 (e약은요 비위험 정보 자연어 요약)
    - ❌ **의료 안내(DUR 위험 안내·진단성 응답) — LLM·RAG 모두 미사용** (식약처 DUR 데이터 → 정해진 템플릿 → 화면·TTS 출력)
- **외부 인터넷 출처 차단**: 약 조합 위험 정보는 식약처 데이터(DUR/e약은요)만 사용. 외부 블로그·논문·인터넷 검색 결과 금지 (법적·의료적 책임 소재 불분명)
- **프롬프트 인젝션 방어**: 사용자 입력이 LLM 분류기·Onboarding LLM을 우회해 의료 안내 영역으로 진입하지 않도록 입력 검증·시스템 프롬프트 락
- **폰 온디바이스 STT — 대역폭·개인정보 이중 최적화**: 음성 바이너리가 서버 구간에 흐르지 않아 트래픽 수백~수천 배 감소 + 음성 원본 비저장. 정확도 부족 시 추론 PC Whisper fallback 어댑터 구조
- **TTS 음성 안내 — 클라 자체 TTS 우선 + 메인 서버 fallback 어댑터**: Qt6 `QTextToSpeech` + Windows SAPI 한국어 (Microsoft Heami / Sun-Hi) 로 텍스트만 흐름·지연 0·운영비 0. 환경 미지원·품질 부족 시 메인 서버 → Google TTS / Naver Clova Voice fallback (어댑터 인터페이스 `ITtsProvider`). 데이터량 비교: 클라 TTS = 텍스트 수백 바이트 / 메인 서버 TTS = 60~180KB MP3 (사진 1장 대비 작지만 클라 TTS 대비 100~300배). 상세 [시스템_연결구조 v2.2 §2.9](시스템_연결구조_ver2.md)

### 6.4 포지셔닝
*"진단"이 아닌 **"안전성 점검 도우미"*** — 약사·의사 상담 안내 톤.

## 7. 본 프로젝트 범위 외 — 추후 검토 사항

> 본 프로젝트는 학생 포트폴리오 범위로 한정. 1차 핵심 모듈(1·2·5·6) MVP 후 다음을 확장 단계에서 진행.

### 7.1 메디브릿지 플랫폼 확장 모듈
- **모듈 3 (증상 / 부작용 기록)** — 텍스트·음성으로 증상 기록, 복용 시각과 매칭. 의료진 인과 추정 보조
- **모듈 4 (헬스케어 데이터 연동)** — 핸드폰 건강 데이터(심박·걸음·수면) + 보고서 통합 (Health Connect / Apple HealthKit)

### 7.2 모듈 2 — 복약 이력 관리 확장
- **음성 → 복약 이력 자동 기록** — "타이레놀 2알 먹었어" → 폰 STT → LLM 추출 → DB 자동 저장
- **음성 → 복약 이력 자연어 조회** — "어제 먹은 약 뭐야?" → DB 조회 + 정해진 템플릿

### 7.3 메디브릿지 플랫폼 확장 기능
- **복약 알림·리마인더** — 시각 알람, 미복용 알림
- **가족·간병인 공유** — 보호자가 환자 복약 상태 모니터링
- **약사·의료진 연계** — 보고서 전자 전송, 표준 양식
- **자유 대화 컨텍스트 유지** — 의료 안내 영역 진입 위험 통제와 함께 별도 설계 필요

### 7.4 모듈 1 — 알약 식별 의료·신뢰성 검증 (사업화 단계)
- **병원·약국과 협업한 안전성 검증** (사용자 테스트, 약사 평가, 임상 환경 시범 운영)
- **유관 단체 자문**: 대한약사회, 환자안전약물관리원(대한약사회 산하), 한국의약품안전관리원(KIDS, 식약처 산하 공공기관)
- **긴급 연결 라인 구축**: 시스템 내 위험 검출 시 응급 연결 (119, 1339 응급의료상담, 약사 직통)
- **정식 의료기기 인증 검토**: 식약처 의료기기 허가/신고, ISO 13485, GMP — 사업화 단계
- **카메라 확장 — Basler pylon**: 산업용 카메라 채택 시 정확도·신뢰성 추가 확보. 컬러 미지원(모노크롬) 가능성 — 도입 시 색상 매칭 fallback 설계 필요
- **STT 확장 — Whisper / Naver Clova fallback**: 폰 STT 정확도 부족 시 어댑터 구조로 SDK만 교체
- **양면 촬영 대안 — 거울 / 지그재그 거치**: Arduino + 스테퍼 모터는 가격·공간 부담 대비 효용 낮음. 카메라 1대 + 거울 또는 지그재그 거치로 양면 동시 촬영 저비용 대안 검토
- **모바일 배포**: 안드로이드 우선 (iOS는 보안 체계상 외부 카메라·외부 통신 제약 큼)
- **복용 스케줄러 알림 기능**: 사용자 복약 시간 등록·알림 (모듈 2 한 단계 발전). 동일 성분 시간차 누적 카운팅(약물동력학 기반 자동 차단)은 본 프로젝트 범위 제외
- **등록 풀 정확도 모니터링**: 등록 약 풀 크기에 따른 매칭 정확도 자동 모니터링 + 임계 초과 시 정리 안내. MVP에서는 사용자 수동 리셋만 제공
