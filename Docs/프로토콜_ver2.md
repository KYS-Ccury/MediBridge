## 1. 시스템 통신 아키텍처 개요

본 프로젝트는 4대의 PC(또는 논리적 분리 환경)와 외부 입력 디바이스(안드로이드 S24 폰), 외부 API를 아우르는 통신 구조를 가집니다.

- **GUI PC ↔ 운용 서버 PC**: TCP/IP 기반 통신. 일반 API는 **REST API(HTTP) 위에서 동작**하며, 카메라 이미지 페이로드는 동일 TCP 채널의 별도 엔드포인트로 송수신.
- **운용 서버 PC ↔ 추론 PC**: HTTP 기반 REST API 통신.
- **운용 서버 PC ↔ 식약처 OpenAPI**: HTTPS. **e약은요(효능·복용법)에 한해 사용자 요청 시점에 lazy 캐싱**할 때만 외부 호출. 낱알식별·DUR 품목·DUR 성분은 식약처 CSV/EXCEL 또는 스마트싱크(MariaDB 자동 동기화)로 **초기 일괄 적재 + 주기적 갱신**(예: 월 1회 또는 수동)이며 운용 중에는 외부 호출이 발생하지 않습니다.
- **학습 서버 → 추론 PC**: SCP / 파일 전송 (모델 배포 시에만 통신).
- **(신규) 안드로이드 S24 폰 ↔ GUI PC**: USB 또는 WiFi. 폰은 카메라 + 마이크 + **온디바이스 STT(Galaxy AI / Android `SpeechRecognizer`)** 를 처리하여, 이미지 바이너리와 STT 결과 **텍스트**를 GUI PC로 전달합니다.

> ⭐ **v2.0 변경 핵심**: 음성은 폰의 온디바이스 STT로 클라이언트 측에서 텍스트로 변환한 뒤 송신합니다. 운용 서버·추론 PC 구간으로 음성 바이너리가 흐르지 않으므로 대역폭 부담과 개인정보 노출 위험이 줄어듭니다. 추론 PC의 Whisper STT 엔드포인트는 **확장 영역(폰 STT 실패 시 fallback)** 으로 분리합니다.

## 2. [GUI PC ↔ 운용 서버 PC] 클라이언트 통신 명세

클라이언트(GUI)와 서버 간의 데이터 교환을 담당합니다. TCP/IP 위에서 동작하며 일반 API는 REST(HTTP), 미디어(이미지)는 동일 TCP 채널의 별도 엔드포인트로 분리됩니다.

### 2.1 사용자 인증 및 계정 (모듈 6)

- **회원가입**
    - `POST /auth/signup`
    - 요청: 아이디(이메일), 비밀번호, 닉네임
    - DB 매핑: `users` 테이블 생성
- **로그인 및 로그아웃**
    - `POST /auth/login`: 아이디/비밀번호 검증 후 세션 또는 토큰(JWT 등) 발급
    - `POST /auth/logout`: 세션/토큰 무효화

### 2.2 복약 이력 및 보고서 (모듈 2, 5)

- **복약 이력 기록**
    - `POST /history/record`
    - 요청: 복용 시각(년·월·일·시·분), 약 이름, 개수, 메모, (선택) 식별 신뢰도, (선택) DUR 위험 검출 결과 스냅샷
    - DB 매핑: `medication_intake_logs` 테이블 저장
- **복약 이력 조회**
    - `GET /history/list`
    - 요청: 일자별, 약별, 기간별 필터 파라미터
- **보고서 생성**
    - `GET /report/generate`
    - 응답: 의사 상담용 통합 보고서 PDF/HTML 반환
    - DB 매핑: `user_reports` 테이블 저장 및 통계 추출

### 2.3 미디어 및 음성 텍스트 송수신

> v1.0 대비 **음성 바이너리 송수신을 제거**했습니다. 음성은 폰 온디바이스 STT 처리 후 텍스트로 송신합니다.

- **이미지 업로드 (카메라 캡처)**
    - `POST /media/image`
    - 요청: 이미지 바이너리(PNG/JPEG, multipart 또는 base64), (선택) 캘리브레이션 정보
    - 응답: 식별 후보(신뢰도 분기 정보 포함), 능동/대화형 가이드 텍스트(TTS용)
- **음성 텍스트 전달**
    - `POST /speech/utterance`
    - 요청: **폰의 온디바이스 STT 결과 텍스트** + 인식 신뢰도(폰이 제공하는 경우) + 발화 컨텍스트(식별 직후/등록 중/일상 질의 등)
    - 응답: 의도 분류 결과(약 식별 / 위험 점검 / 정보 확인 / 등록 / 복약 이력 조회 / 보고서 출력 / 기타) 또는 정규화된 약명 후보
- **(확장) 음성 바이너리 fallback**
    - `POST /speech/audio` — 폰 온디바이스 STT 미사용·실패 시에만 사용. MVP 미구현. 서버는 추론 PC `/speech/stt`(확장 fallback)로 위임.

### 2.4 입력 디바이스 (안드로이드 S24 폰) 동작 정의

- **카메라**: 다중 알약 사진 촬영 → GUI PC로 전송 → 운용 서버 `/media/image`로 업로드.
- **마이크 + 온디바이스 STT**: 사용자 발화를 실시간으로 텍스트 변환. 변환된 텍스트를 GUI PC로 전달 → 운용 서버 `/speech/utterance`로 송신.
- **연결 방식**: USB 직결(권장) 또는 WiFi(폰-PC 동일 네트워크).
- **장점**: 음성 바이너리가 네트워크에 흐르지 않아 대역폭 절감 + 개인정보 노출 위험 감소.

## 3. [운용 서버 PC ↔ 추론 PC] AI REST API 명세

운용 서버가 AI 추론 모델을 호출하기 위해 추론 PC로 전송하는 내부 REST API 통신 규격입니다.

### 3.1 Vision 영역 (알약 식별)

- **알약 검출 및 Crop (YOLO26)**
    - `POST /vision/detect`
    - 요청: 이미지 바이너리(PNG/JPEG)
    - 응답: `[{ bbox, crop_id, confidence }]`, 상태 코드 (능동 가이드 트리거용)
- **각인 인식 및 색상/모양 분석 (PaddleOCR + OpenCV)**
    - `POST /vision/analyze`
    - 요청: Crop된 알약 이미지
    - 응답: 각인 텍스트, 색상(HSV), 모양 분류 결과, 신뢰도 값

### 3.2 Speech 영역 (음성 인식 — 확장 fallback)

> ⭐ **v2.0 변경**: MVP는 폰 온디바이스 STT를 채택하므로 본 절은 **확장 fallback** 영역입니다. MVP 구현 대상에서 제외합니다.

- **(확장) 음성 텍스트 변환 (Whisper STT)**
    - `POST /speech/stt`
    - 요청: 오디오 바이너리 데이터
    - 응답: 변환된 텍스트 및 인식 신뢰도
    - 사용 시점: 폰 온디바이스 STT를 사용할 수 없는 디바이스가 추가되거나, 정확도 검증 단계에서 비교 평가가 필요할 때.

### 3.3 LLM 및 Intent(의도 분류) 영역

- **일상 사용 의도 분류 (Stage 0.5)**
    - `POST /intent/classify`
    - 요청: 사용자 발화 텍스트(폰 온디바이스 STT 결과) (±이미지 컨텍스트)
    - 응답: 의도 카테고리 라벨 (약 식별/위험 점검/정보 확인/등록 요청/복약 이력 조회/보고서 출력/기타), 신뢰도 (반드시 JSON 스키마 형식으로만 반환)
- **등록(Onboarding) 약명 정규화**
    - `POST /onboarding/normalize`
    - 요청: 폰 STT로 인식된 약명 텍스트
    - 응답: 정규화된 약명 후보
- **동명/동성분 분기 질문 생성**
    - `POST /onboarding/disambiguate`
    - 요청: 동명 약 후보 리스트
    - 응답: 분기를 위한 사용자 질문 텍스트
- **비위험 정보 일반 안내 (e약은요 RAG)**
    - `POST /summary/non-medical`
    - 요청: 효능, 복용법 등 식약처 비위험 정보 원문
    - 응답: 자연어로 요약된 TTS 출력용 텍스트

## 4. [운용 서버 PC ↔ 외부 / DB] 통신 규약

- **식약처 OpenAPI 연동**: HTTPS 방식. **낱알식별 / DUR 품목 / DUR 성분**은 식약처 CSV/EXCEL 또는 스마트싱크로 **MariaDB에 일괄 적재 + 주기적 갱신**(예: 월 1회 또는 수동)이며 운용 중 외부 호출 없음. **e약은요(효능·복용법)** 만 사용자 요청 시점에 **lazy 캐싱** — 1차 조회는 로컬 DB, 캐시 미스 시 외부 호출 후 DB에 누적 저장. (※ v1.0의 "TTL 30일" 만료 정책은 폐기)
- **MariaDB 통신**: 운용 서버는 SQL 인젝션 방어를 위해 반드시 파라미터 바인딩을 사용하여 DB와 통신합니다. 연동 시 `pill_ingredient_mapping`을 통해 특정 약의 성분을 역추적하고 `dur_interaction_cache`에서 병용금기 위험을 점검합니다.
