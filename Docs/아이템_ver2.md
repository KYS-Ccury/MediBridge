# 특이사항

- **외부 지식 데이터(External Knowledge Sources)는 필요한 곳에만** — 단순 lookup으로 풀리는 문제에 RAG 구조를 끼워 맞추지 않음
- **개발 ~ 배포 전 과정 경험** 가능한 범위로 한정

> **용어 메모**: 본 프로젝트의 외부 지식 데이터(식약처 데이터 4종)는 **Rule-based 조회를 우선**으로 하되, **비의료 영역(약 정보 등록·일반 안내)에 한해 RAG 활용을 허용**한다. 의료 안내 영역(DUR 위험 안내·진단성 응답)에는 LLM·RAG 모두 미사용한다. 식별·DUR의 핵심 데이터(낱알식별·DUR 품목·DUR 성분)는 식약처 CSV/EXCEL 또는 스마트싱크(MariaDB 자동 동기화)로 일괄 적재하고, e약은요(효능·복용법)는 사용자 요청 시점에 lazy 캐싱한다(만료 정책 없음).

## 🥇 메디브릿지 (MediBridge) — 복약·건강 통합 케어 플랫폼

### **한 줄 컨셉**

**메디브릿지** — 알약 식별·복약 이력·증상·헬스케어 데이터를 통합해 의사 상담용 보고서로 연결하는 **복약·건강 통합 케어 플랫폼**.

본 프로젝트(MVP) 범위는 그중 **모듈 1: 알약 식별 + 안전 점검** 을 중심으로, 모듈 2(복약 이력), 모듈 5(통합 보고서), 모듈 6(인증)을 함께 구현한다. 모듈 1은 알약 사진(여러 알 동시 촬영 가능)과 음성 질문(폰 온디바이스 STT 결과 텍스트)으로 약을 식별하고, 식약처 DUR과 결합해 병용금기·중복 처방 위험을 점검하는 한국 식약처 데이터 기반의 국내 알약 식별 도구이다.

### 메디브릿지 플랫폼 모듈 구조

| # | 모듈 | 본 프로젝트 (MVP) | 비고 |
| --- | --- | --- | --- |
| **1** | **알약 식별 + 안전 점검** | ✅ 핵심 | YOLO26·PaddleOCR·OpenCV·LLM·식약처 DUR. 사전 등록 약 풀 기반. 본 문서 대부분이 모듈 1 명세 |
| **2** | **복약 이력 관리** | ✅ 포함 | 복용 시각·약·개수·메모. 일자별·약별 조회 |
| **3** | 증상 / 부작용 기록 | ⚠️ 확장 | 사용자가 느낀 증상을 텍스트·음성으로 기록. 복용 시각과 매칭하여 의료진 인과 추정 보조 |
| **4** | 헬스케어 데이터 연동 | ⚠️ 확장 | 핸드폰 심박·걸음·수면·활동량 (Health Connect / HealthKit) |
| **5** | **통합 보고서** | ✅ 포함 | 의사 상담용 인쇄/PDF. MVP는 약 정보 + 복약 이력 + 식약처 부작용 인용. 확장에서 모듈 3·4 데이터 추가 |
| **6** | **사용자 계정 / 인증** | ✅ 포함 (공통 인프라) | 회원가입·로그인. 모듈 간 사용자 데이터 통합 |

### 확장 로드맵 (본 프로젝트 범위 외)

- **음성 → 복약 이력 자동 기록** ("타이레놀 2알 먹었어" → 폰 STT → LLM 추출 → DB 저장)
- **음성 → 복약 이력 자연어 조회** ("어제 먹은 약 뭐야?" → DB 조회 + 템플릿 출력)
- **복약 알림·리마인더, 가족·간병인 공유, 약사·의료진 연계, 자유 대화 컨텍스트**

### **타깃 사용자**

- **주 타깃**: **고령층** (음성 인터페이스 기반 쉬운 접근성, 복약 혼동 예방)
- **보조 타깃**: 청·장년층 (다제 복용 자가 관리, 사전 등록 기반 체계적 복약 관리)
- 유니버설 디자인 사상은 적용하되, 핵심 시나리오·시장 근거는 고령층 중심으로 유지

    - **[주 타깃] 일반의약품 자가 구매 시 안내 누락 보완**: 동일 약국에서 진통제와 감기약을 함께 사면 약사가 동일 성분 중복(아세트아미노펜 등)을 안내하지만, 다른 약국·다른 시점에 별도 구매 시 안내 누락 — 사용자가 모든 약을 등록해두면 시스템이 DUR로 위험 자동 검출
    - **[보조 타깃] 청·장년층의 체계적 복약 관리**: 처방약·일반의약품·영양제 등 다양한 약 동시 복용 시 중복 성분·상호작용 인지 어려움 — 사전 등록 후 새로운 약 추가 시 자동 DUR 점검, 음성 질문으로 신속한 정보 확인 (예: "이 약 공복에 먹어도 돼?")
    - **[모듈 5 — MVP] 의사 상담 시 통합 보고서 출력**: 사용자가 복용한 약의 종류·개수·이름·복용 시각을 보고서로 출력해 의사·약사에게 제출. 약별 부작용 주요 증상은 식약처 e약은요 데이터에서 인용. 인쇄 또는 PDF 형태 (MVP 시나리오)
    - **[확장] 음성으로 복약 이력 기록**: "타이레놀 2알 먹었어" 발화 → 폰 STT → LLM 추출 → 복약 이력 DB 자동 저장 (확장 시나리오)
    - **[확장] 헬스케어 데이터 통합 보고서**: 핸드폰 건강 데이터(심박수·걸음수·수면)를 복약 이력과 함께 통합 보고서에 표기 (확장 시나리오)

**기술 스택 (예비) — OCR 중심 식별 + Rule-based DB 매칭 (+ 비의료 영역 RAG)**

- 알약 검출: YOLO26 (각 알약 bounding box)
- 각인 OCR: PaddleOCR + 알약 데이터 fine-tuning (가장 중요)
- 색상 분석: OpenCV HSV 히스토그램 (핸드폰 카메라는 컬러 가능, pylon 확장 시 사양에 따라 모노크롬 가능성 존재)
- 형상 분석: OpenCV 윤곽선 + 모양 분류
- DB 매칭: 식약처 낱알식별 API의 검색 키(각인·모양·색상)를 그대로 활용 — Rule-based
- 위험 검출: 식약처 DUR API 직접 조회 (운용 중 외부 호출 없음, 일괄 적재본 사용)
- 보조용 CNN: 각인 인식 실패 시 fallback (ResNet 등)
- 백엔드: FastAPI + MariaDB (**GUI PC + 운용 서버 PC + 추론 PC + 학습 서버 4대 분리** 구조, **메인 DB는 운용 서버의 MariaDB 단일** — 클라우드 DB는 보류)
- **식약처 데이터 적재**: 낱알식별·DUR 품목·DUR 성분은 식약처가 제공하는 **CSV/EXCEL 파일 일괄 다운로드** 또는 **스마트싱크(MariaDB 자동 동기화 도구)** 로 초기 적재 + 주기적(예: 월 1회 또는 수동) 갱신. e약은요(효능·복용법·주의사항·부작용)는 사용자가 등록·조회한 약만 lazy 캐싱(만료 정책 없음). 운용 중 외부 API 호출은 거의 발생하지 않음
- 위험 안내 출력: 식약처 DUR 데이터 → 정해진 템플릿 → 화면·TTS 출력 (LLM·RAG 모두 미사용)
- LLM·RAG 활용 (영역 한정):
    - **약 정보 등록(Onboarding)** ✅ RAG 허용: 폰 STT 결과 약명 추출·정규화, 직접 입력 시 모호한 약명 후보 추천, 등록 시 동명·동성분 약 후보 분기 질문 생성, 등록 확인 단계 e약은요 자연어 요약
    - **일상 사용 시 의도 분류기 (Stage 0.5)**: 사용자 음성 발화 카테고리 분류만 수행 (응답 생성 X)
    - **비의료 일반 안내 보조** ✅ RAG 허용: e약은요 비위험 정보 자연어 요약
    - **의료 안내(DUR 위험 안내)** ❌ LLM·RAG 모두 미사용 — 정해진 템플릿만 사용
    - **외부 인터넷 출처 사용 금지**: 약 조합 위험 정보는 식약처 DUR/e약은요 데이터만 사용. 외부 블로그·논문·인터넷 검색 결과 사용 X
    - **프롬프트 인젝션 방어**: 사용자 입력이 분류기·Onboarding LLM을 우회해 의료 안내 응답 생성 영역으로 진입하지 않도록 입력 검증·시스템 프롬프트 락 적용
- **음성 인식(STT) — MVP**: **안드로이드 S24 폰의 온디바이스 STT (Galaxy AI / Android `SpeechRecognizer`)** — 음성 바이너리가 서버 구간에 흐르지 않아 대역폭 절감 + 개인정보 노출 위험 감소
- **음성 인식(STT) — 확장 fallback**: 추론 PC Whisper STT (`POST /speech/stt`) → 정확도 향상 시 Naver Clova Speech로 교체 가능
- 음성 합성(TTS): **Google TTS** (또는 시스템 TTS) — 능동/대화형 가이드, 등록 확인, 결과 안내, 위험 검출 안내에 사용
- 등록 약 DB: MariaDB 사용자별 약 풀 테이블 — **추가 / 삭제(soft delete) / 전체 리셋(사용자 수동 트리거만)** 지원
- **모듈 6 (사용자 계정 / 인증)**: 회원가입·로그인 (FastAPI + 세션/토큰, JWT 등). 비밀번호는 bcrypt 등 표준 해시로 저장. 모든 약 풀·복약 이력 API는 인증된 사용자에 한해 본인 데이터만 접근. 파라미터 바인딩으로 SQL 인젝션 방어
- **모듈 2 (복약 이력 관리)**: MariaDB 복약 이력 테이블 — 복용 시각(년·월·일·시·분)·약 이름·개수·메모 + (선택) 식별 신뢰도·DUR 스냅샷. 시각 미입력 시 시스템 시각 자동 사용. 일자별·약별·기간별 필터 조회. 시각은 분 단위까지 저장되어 아침/점심/저녁/취침 자동 분류 가능
- **모듈 5 (통합 보고서)**: 지정 기간의 복약 이력을 표 형태로 출력. 약별 부작용 주요 증상은 식약처 e약은요 데이터(주의사항·부작용 항목)에서 인용한 형태로 표시(LLM 자연어 생성 미사용). 인쇄 또는 PDF 출력. 확장에서 모듈 3·4 데이터 통합
- GUI: **Qt6 + C++ + QML** — 교수 요구사항(C++) 직접 충족. **기능 단위 모듈 분리**(폰 입력 수신 / 결과 표시 / 사용자 입력 / TTS 클라이언트) 적용
- **일상 사용 입력 채널**: 카메라 촬영 + **음성 질문(폰 온디바이스 STT)** (둘 중 하나 또는 결합)
- **능동/대화형 가이드**: 능동 가이드(시스템이 먼저 안내, 예: "카메라로 약을 비춰주세요") + 대화형 가이드(인식 결과에 따른 추가 요청, 예: "약을 눕혀주세요", "다시 확인하시겠습니까")
- **통신**: TCP/IP **(GUI PC ↔ 운용 서버, 운용 서버 ↔ 추론 PC) — 두 구간 모두 REST API(HTTP) 위에서 동작**. 통신 ①(GUI ↔ 운용 서버)은 일반 API와 미디어(이미지)·STT 텍스트 별도 엔드포인트로 분리. HTTPS (식약처 OpenAPI는 e약은요 캐시 미스 시에만 호출)
- 하드웨어:
    - **MVP**: **안드로이드 S24 폰** (GUI PC에 USB 직결 또는 WiFi 전송) — 카메라 + 마이크 + 온디바이스 STT 통합 처리
    - **확장**: Basler pylon (GUI PC USB 직결) + Ring Light (단면 촬영 정확도 보강 시)
    - **Arduino 미사용**: 회전 거치대(스테퍼 모터)는 1년에 수회 사용되는 기기 특성상 가격·공간 부담 대비 효용이 낮음. 양면 촬영은 단면 촬영 + 사용자 가이드(앞뒷면 뒤집기)로 대체. 부저/LED는 본 프로젝트 범위 외

> 참고: AI Hub 베이스라인 모델은 ResNet152 분류기였으나 **AI Hub 공식 측정값 기준 Top-5 정확도 10%** (기준값 90%)로 매우 낮음 — 5,000종 단순 분류의 한계 입증. 본 프로젝트는 OCR + Rule-based DB 매칭으로 우회.
(출처: AI Hub 경구약제 이미지 데이터 페이지 "데이터 성능 지표" 섹션)

**핵심 설계 원칙 — 한계와 대응**

**모듈 1 (알약 식별 + 안전 점검)** 의 설계 원칙:

- 알약 5,000종 중 정확한 1:1 식별은 본질적으로 어려움 (외형 유사성 + 각인의 미세함)
- 따라서 **사전 등록 + 다층 안전 메커니즘 + 2단계 추론 시스템**으로 설계
- 사전 등록 (Onboarding)**으로 식별 범위를 5,000종 → 등록된 N종으로 좁혀 정확도를 본질적으로 해결:
    - **음성 인식 등록**: 폰 온디바이스 STT로 약명 입력 → 식약처 DB 검색 → 사용자 확인. LLM이 동명·동성분 약 후보를 분기 질문으로 정리(예: "예전에 드셨던 OO약인가요? 최근 드시는 OO약인가요?")
    - **직접 입력 등록**: 약명·각인 입력 → 식약처 DB 검색
    - **단일 촬영 등록**: 알약 한 알 정밀 촬영 → Top-N 후보 → 사용자 선택 (확장 범위)
    - **확인 절차**: 음성 응답 또는 화면 클릭 (사용자 환경 선택)
    - **등록 약 관리**: 추가 / 삭제(soft delete) / **전체 리셋(사용자 수동 트리거만)** 지원 — 분류 카테고리 누적 시 정확도 저하 방지
- **일상 사용 흐름** (3단계):
    - **Stage 0.5 (음성 입력 시에만)**: LLM 의도 분류기 → 카테고리 분류(약 식별/위험 점검/일반 정보 확인/등록 요청/복약 이력 조회/보고서 출력). 응답 생성 X. 정보 부족 시 능동/대화형 가이드 (TTS)
    - **Stage 1**: 검출 → OCR(각인) + 색·모양 분석 → 등록된 N종 풀에서 매칭
    - **Stage 2**: 식별된 약 조합을 DUR API로 조회 → 위험 자동 검출 (정해진 템플릿으로 출력)
- **다층 안전 메커니즘**:
    - **사전 등록 효과**: 식별 범위가 5,000종 → 사용자 N종으로 축소되어 매칭 정확도 본질적 향상 (AI Hub 베이스라인 Top-5 10%의 한계 우회)
    - **하드웨어 보강**: 안드로이드 S24 폰(MVP)으로 미세 각인 인식, 확장 시 pylon 산업 카메라 + Ring Light로 정확도 추가 보강 (360도 양면 촬영은 본 프로젝트 범위 외)
    - **신뢰도 단계 메시지**: 95%↑ 표시형 / 70~95% 후보 비교형 / 70%↓ 식별 불가 안내
    - **표현 톤**: 모든 결과를 "추정" + "식약처 DUR 인용" + "약사·의사 상담 권유" 톤으로 통일. **단정 문구("복용 가능합니다 / 불가합니다") 사용 금지**. 안전 케이스도 단정 X — "DUR 등록 확인되지 않음 + 약사·의사 상담 권유"로 출력
    - **LLM·RAG 활용 영역 제한**: 알약 검출(YOLO26), OCR(PaddleOCR), **음성 인식(폰 온디바이스 STT, 확장 fallback Whisper)** 등 변환·인식 AI는 사용. **의료 안내(DUR 위험 안내) 영역에는 LLM·RAG 모두 미사용** — 식약처 DUR 데이터를 정해진 템플릿으로만 출력. **LLM·RAG는 ① 약 정보 등록(Onboarding) 단계, ② 일상 사용 시 의도 분류기 (Stage 0.5, 분류만 수행, 응답 생성 X), ③ 비의료 일반 안내 보조에 한정해 활용**. LLM Agent 오케스트레이터 구조도 같은 영역에만 적용. 대규모 언어 모델(GPT/Claude 등)이 의료 정보를 자연어로 창작·변환하는 것은 환각·왜곡으로 인한 잘못된 의료 안내(진단성 응답)의 법적 리스크가 있어 차단
    - **외부 인터넷 출처 차단**: 약 조합 위험 정보는 식약처 데이터(DUR/e약은요)만 사용. 외부 블로그·논문·인터넷 검색 결과는 법적·의료적 책임 소재가 불분명해 사용 금지
    - **프롬프트 인젝션 방어**: 사용자 음성·텍스트 입력이 LLM 분류기 또는 Onboarding LLM을 우회해 의료 안내 영역으로 진입하지 않도록 입력 검증·시스템 프롬프트 락 적용
    - **(v2.0) 폰 온디바이스 STT — 대역폭·개인정보 이중 최적화**: 음성 바이너리가 서버 구간에 흐르지 않아 트래픽 수백~수천 배 감소 + 음성 원본 비저장(개인정보 보호). 정확도 부족 시 추론 PC Whisper로 fallback 가능한 어댑터 구조
- 포지셔닝: *"진단"이 아닌 **"안전성 점검 도우미"*** — 약사·의사 상담 안내 톤

1. 한 줄 컨셉 / 타겟 사용자
2. 시장성 / 상업적 활용 시나리오

## 본 프로젝트 범위 외 — 추후 검토 사항

> 본 프로젝트는 학생 포트폴리오 범위로 한정한다. 메디브릿지 플랫폼의 1차 핵심 모듈(모듈 1·2·5·6)을 MVP로 구현한 뒤, 다음 모듈·기능을 확장 단계에서 진행한다.

### 메디브릿지 플랫폼 확장 모듈

- **모듈 3 (증상 / 부작용 기록)** — 텍스트·음성으로 증상을 기록하여 복용 시각과 매칭. 의료진의 인과 추정 보조
- **모듈 4 (헬스케어 데이터 연동)** — 핸드폰 건강 데이터(심박·걸음·수면) 수집 + 보고서 통합 (Health Connect / Apple HealthKit)

### 모듈 2 — 복약 이력 관리 확장

- **음성 → 복약 이력 자동 기록** — "타이레놀 2알 먹었어" 발화 → 폰 STT → LLM 추출 → DB 자동 저장
- **음성 → 복약 이력 자연어 조회** — "어제 먹은 약 뭐야?" → DB 조회 + 정해진 템플릿 출력

### 메디브릿지 플랫폼 확장 기능

- **복약 알림·리마인더** — 시각 알람, 미복용 알림
- **가족·간병인 공유** — 보호자가 환자 복약 상태 모니터링
- **약사·의료진 연계** — 보고서 전자 전송, 표준 양식
- **자유 대화 컨텍스트 유지** — 의료 안내 영역 진입 위험 통제와 함께 별도 설계 필요

### 모듈 1 — 알약 식별 의료·신뢰성 검증 (사업화 단계)

- **병원·약국과 협업한 안전성 검증** (모듈 1)
    - 사용자 테스트, 약사 평가, 임상 환경 시범 운영
- **유관 단체 자문**
    - 대한약사회, 환자안전약물관리원(대한약사회 산하), 한국의약품안전관리원(KIDS, 식약처 산하 공공기관) 등
- **긴급 연결 라인 구축**
    - 시스템 내 위험 검출 시 응급 연결 (119, 1339 응급의료상담, 약사 직통)
- **정식 의료기기 인증 검토**
    - 식약처 의료기기 허가/신고, ISO 13485, GMP 등은 본 프로젝트 범위 외
    - 사업화 단계에서 별도 검토
- **카메라 확장 — Basler pylon**
    - 산업용 카메라 채택 시 정확도·신뢰성 추가 확보 가능. 단, 컬러 미지원(모노크롬) 가능성 있어 도입 시 색상 매칭 fallback 설계 필요
- **STT 확장 — 추론 PC Whisper fallback**
    - 폰 온디바이스 STT 정확도 부족 시 추론 PC Whisper로 fallback 또는 Naver Clova Speech 교체. 어댑터 구조로 분리되어 있어 SDK만 교체
- **양면 촬영 대안 — 거울 / 지그재그 거치**
    - 회전 거치대(Arduino + 스테퍼 모터)는 가격·공간 부담 대비 효용 낮음. 카메라 1대 + 거울 또는 지그재그 거치로 양면을 동시 촬영하는 저비용 대안을 추후 검토
- **모바일 배포**
    - 안드로이드 우선 (iOS는 보안 체계상 외부 카메라·외부 통신 제약 큼). 추론 모델 경량화 및 온디바이스 추론 비용 효율성 검증 필요
- **복용 스케줄러 알림 기능** (확장)
    - 사용자 복약 시간 등록·알림 (MVP의 모듈 2 복약 이력 기록에서 한 단계 더 발전된 기능). 동일 성분 시간차 누적 카운팅(약물동력학 기반 자동 차단)은 본 프로젝트 범위에서도 제외
- **등록 풀 정확도 모니터링**
    - 등록 약 풀 크기에 따른 매칭 정확도 자동 모니터링 + 임계 초과 시 정리 안내. MVP에서는 사용자 수동 리셋만 제공
