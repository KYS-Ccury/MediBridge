# 1. 시스템 개요

### 1.1 한 줄 컨셉

**메디브릿지 (MediBridge)** — 알약 식별·복약 이력·증상·헬스케어 데이터를 통합해 의사 상담용 보고서로 연결하는 **복약·건강 통합 케어 플랫폼**.

본 문서가 다루는 시스템 흐름은 메디브릿지 플랫폼 전체 흐름과 그중 본 프로젝트(MVP)에서 구현하는 **모듈 1(알약 식별 + 안전 점검) + 모듈 2(복약 이력) + 모듈 5(통합 보고서) + 모듈 6(인증)** 의 처리 흐름이다.

### 1.2 타깃 사용자

- **주 타깃: 고령층** — 음성 인터페이스 기반의 쉬운 접근성 제공, 복약 혼동 예방이 핵심 가치
- **보조 타깃: 청·장년층** — 바쁜 일상 속 중복 복용 방지, 사전 등록 기반의 체계적 복약 관리
- 유니버설 디자인 사상은 적용하되, 핵심 시나리오·시장 근거(다제병용 70.2%, 약국 사고 65세 이상 61.7%)는 고령층 중심으로 유지

### 1.3 포지셔닝

- "진단" 도구가 ❌ 아닌 **"안전성 점검 도우미"** ✅
- 약사·의사 상담 권유 톤 일관 유지
- **국내 알약(식약처 OpenAPI 등재) 한정** — 해외 약은 본 프로젝트 범위 외

### 1.4 핵심 설계 원칙

**사전 등록 + 다층 안전 메커니즘 + 2단계 추론 시스템 + 식약처 데이터 일괄 적재 + 사용자 인증 기반 데이터 분리 + 폰 온디바이스 STT**

### 1.5 메디브릿지 플랫폼 모듈 구조

| # | 모듈 | 본 프로젝트 (MVP) | 비고 |
| --- | --- | --- | --- |
| **1** | **알약 식별 + 안전 점검** | ✅ 핵심 | YOLO26·PaddleOCR·OpenCV·LLM·식약처 DUR. 본 문서 2~5장 대부분이 모듈 1 흐름 |
| **2** | **복약 이력 관리** | ✅ 포함 | 복용 시각·약·개수·메모 기록, 일자별·약별 조회 |
| **3** | 증상 / 부작용 기록 | ⚠️ 확장 | 사용자가 느낀 증상을 텍스트·음성으로 기록 |
| **4** | 헬스케어 데이터 연동 | ⚠️ 확장 | 핸드폰 심박·걸음·수면 (Health Connect / HealthKit) |
| **5** | **통합 보고서** | ✅ 포함 | 의사 상담용 인쇄/PDF |
| **6** | **사용자 계정 / 인증** | ✅ 포함 (공통 인프라) | 회원가입·로그인. 모듈 간 사용자 데이터 통합 |

### 1.6 확장 로드맵 (본 프로젝트 범위 외)

- 음성 → 복약 이력 자동 기록 ("타이레놀 2알 먹었어")
- 음성 → 복약 이력 자연어 조회 ("어제 먹은 약 뭐야?")
- 복약 알림·리마인더, 가족·간병인 공유, 약사·의료진 연계, 자유 대화 컨텍스트

## 2.1 PC 구성 및 통신 구조 ⭐ v3.0 갱신

### 설계 의도

- **GUI PC가 폰 입력 디바이스를 수신**: 사용자 환경(가정·요양원)에 GUI PC가 놓이고, 폰이 카메라·마이크·STT를 모두 처리해 GUI PC로 전달. GUI PC는 결과를 운용 서버로 송신하고 응답을 표시. 폰은 MVP에서 안드로이드 S24를 채택(컬러 가능, 온디바이스 AI 지원), 확장에서 pylon(정확도 보강) 사용
- **음성 바이너리 송수신 제거**: 폰 온디바이스 STT(Galaxy AI / Android `SpeechRecognizer`)로 텍스트 변환 후 송신하므로, 운용 서버·추론 PC 구간에 음성 바이너리가 흐르지 않음 → 대역폭 절감 + 개인정보 노출 위험 감소. 추론 PC Whisper는 확장 fallback
- **운용 서버 ↔ 추론 PC 분리**: AI 추론을 별도 GPU PC로 분리해 자원 경합 방지, MLOps 관점의 추론 서비스 구조 확보. 통신 ②는 REST API on HTTP로 단일화해 디버깅·확장 용이성 확보
- **학습 서버 별도**: 학습/운용 분리 요구사항(기획서 2.1) 직접 충족. 학습 환경의 GPU·메모리 부담이 운용에 영향 주지 않도록 격리
- **TCP/IP 활용 지점**: 1·2번 구간에서 명시적으로 TCP/IP를 사용 — 교수 요구사항 직접 충족
- **외부 API 의존 최소화 — 일괄 적재 + lazy 캐싱**: 낱알식별·DUR 품목·DUR 성분은 식약처 CSV/EXCEL 또는 스마트싱크(MariaDB 자동 동기화 도구)로 MariaDB에 일괄 적재 + 주기적 갱신. e약은요(효능·복용법)는 사용자 요청 시점에 lazy 캐싱(다음 조회부턴 DB에서 반환). 운용 중 외부 API 호출이 거의 발생하지 않으며, 외부 API 장애 시에도 식별·DUR 핵심 기능은 영향 없음. **(v2.0)** TTL 30일 만료 정책은 폐기 — 단순 주기 갱신 + lazy 캐싱으로 통일

### ⚠️ 일정 리스크

PC 4대 분리 구성은 환경 구성·디버깅·배포 부담이 큼. 몇 주 일정 안에 통합 테스트까지 마치려면:

- 초기 개발은 단일 PC 또는 2대 환경에서 시작 → 통합 단계에서 4대로 분리 배포
- 또는 PC 부족 시 한 PC에 여러 서버를 컨테이너/프로세스로 분리해 논리적 분리 유지

## 3. 단계별 상세

### 3.1 [Stage 0] 사전 등록 — 정확도 본질 해결

### 등록 방법 3가지

| 방법 | 흐름 | 필요 기술 | 범위 |
| --- | --- | --- | --- |
| 음성 인식 | 사용자 발화 → **폰 온디바이스 STT** → 텍스트 → 식약처 캐시 검색 → 후보 표시 → (필요 시) 동명·동성분 분기 질문 → 사용자 확인 | 폰 온디바이스 STT (MVP) + LLM 분기 질문 생성 (RAG 허용) | MVP |
| 직접 입력 | 약명/각인 키보드 입력 → 식약처 캐시 검색 → 후보 표시 → 사용자 확인 | 식약처 낱알식별 캐시 (MariaDB 미러링) | MVP |
| 단일 촬영 | 알약 한 알 정밀 촬영 → CV 분석 → Top-N 후보 → 사용자 선택 | YOLO26 + PaddleOCR + OpenCV | 확장 |

### 동명·동성분 약 분기 질문 (LLM, Onboarding 영역, RAG 허용)

- 동일 약명의 여러 등록 후보가 있을 때, LLM이 사용자에게 분기 질문 생성
- 예: "예전에 드셨던 OO약(혈압약)인가요? 최근 드시는 OO약(진통제)인가요?"
- 의료 안내 영역이 아닌 **등록(Onboarding) 영역**이므로 LLM·RAG 활용 가능

### 확인 절차

- 화면 클릭 또는 음성 응답
- 사용자 환경 (가정/요양원/시각장애 등)에 따라 선택

### 등록 약 관리

- **추가**: 신규 약 등록 (위 3가지 방법)
- **삭제**: 더 이상 복용하지 않는 약 개별 삭제 (DB는 soft delete, `is_active = FALSE`)
- **전체 리셋**: 사용자가 수동으로 "전체 초기화" 버튼을 눌렀을 때만 작동 (시스템이 임의로 리셋 X)
- **사유**: 등록 풀이 누적되면 분류 카테고리 증가 → 매칭 정확도 저하. 사용자가 직접 정리할 수 있도록 권한 제공

### 핵심 효과

- 식별 범위가 **5,000종 → 사용자 N종** (예: 30종)으로 축소
- AI Hub 베이스라인 ResNet152 Top-5 정확도 10%(AI Hub 공식 측정값, 기준 90%)의 한계를 **시스템 설계로 우회**

### 3.2 [Stage 1] 일상 식별 — 검출 + 인식 + 매칭

### 입력

- **MVP**: 안드로이드 S24 폰 카메라로 다중 알약 동시 촬영 (컬러 정보 활용 가능)
- **확장**: Basler pylon 산업 카메라 + Ring Light로 측면 조명 → 각인 그림자 강조 (모노크롬 가능성 있어 도입 시 색상 매칭 fallback 설계 필요)

> 참고: 360도 회전 거치대로 알약 양면 촬영하는 구성은 본 프로젝트 범위 외(추후 검토 사항). 본 프로젝트는 단면 촬영 + 사용자 가이드(앞뒷면 뒤집기)로 진행. 양면 동시 촬영 대안으로 거울/지그재그 거치는 추후 검토.

### 처리 파이프라인

```
[Raw Image]
     ↓
[YOLO26] → 알약별 bounding box + crop
     ↓
각 알약마다 병렬:
   ├─ [PaddleOCR] → 각인 텍스트 ("GS-7", "K100" 등)
   ├─ [OpenCV HSV] → 색상 분류 (핸드폰 컬러 / pylon 도입 시 fallback)
   ├─ [OpenCV 윤곽선] → 모양 분류 (원/타원/캡슐형)
   └─ [캘리브레이션] → 크기 측정 (mm)
     ↓
[식약처 낱알식별 캐시] ← 검색 키: 각인 + 모양 + 색상
     ↓
[등록된 N종 풀에서 매칭] → Rule-based 점수 + 신뢰도
```

### 능동/대화형 가이드 (TTS)

- **능동 가이드**: 시스템이 먼저 안내 — "카메라로 약을 비춰주세요"
- **대화형 가이드**: 인식 결과에 따른 추가 요청
    - "약이 서 있어요. 눕혀주세요"
    - "각인이 보이지 않습니다. 다시 확인하시겠습니까?"
    - "식별 결과 후보가 여러 개입니다. 화면에서 선택해주세요"

### 신뢰도별 표시 분기

| 신뢰도 | 메시지 형태 |
| --- | --- |
| 95% ↑ | "○○정으로 추정" (단일 결과 표시형) |
| 70~95% | "다음 후보 중 하나로 추정" (Top-3 비교형) |
| 70% ↓ | "식별 어려움. 약사·의사 확인 권유" |

### 3.3 [Stage 2] 위험 검출 — DUR API + 정해진 템플릿

### 처리 파이프라인

```
[식별된 약 조합 — 예: A정 + B정 + C정]
     ↓
[식약처 DUR 캐시 조회] (MariaDB 일괄 적재본 조회, 외부 호출 없음)
     ↓
8종 위험 카테고리 점검:
   ① 병용금기              ← MVP 우선 구현
   ② 특정연령대금기        ← 확장 범위
   ③ 임부금기              ← 확장 범위
   ④ 용량주의              ← 확장 범위
   ⑤ 투여기간주의          ← 확장 범위
   ⑥ 노인주의              ← 확장 범위
   ⑦ 효능군중복주의        ← 확장 범위
   ⑧ 서방정분할주의        ← 확장 범위
     ↓
[정해진 템플릿] (LLM·RAG 미사용)
     ↓
화면 표시 + TTS 음성
```

### 정해진 템플릿 — 위험 케이스

```
[병용금기]
약 A + 약 B
사유: <DUR 데이터 그대로 인용>
조치: 즉시 약사·의사 상담 필요
```

### 정해진 템플릿 — 안전 케이스

```
[안전 안내]
약 A + 약 B의 부작용은 식약처 DUR에 등록 확인되지 않았습니다.
안심을 위해 약사·의사 상담을 권유드립니다.
```

### 표현 톤 — 단정 문구 금지 ⭐

- ❌ "복용 가능합니다" / "복용 불가합니다" 등 단정 표현 사용 금지
- ✅ 항상 "추정" + "DUR 인용 또는 미등록 표기" + "약사·의사 상담 권유" 톤
- LLM·RAG가 의료 안내 영역에 진입하지 않으므로, 단정 표현이 새어 나갈 가능성 자체를 차단

→ LLM 자연어 변환 차단 (환각·왜곡 방지)

## 4. 다층 안전 메커니즘 (의료 안전성 관점)

### 4.1 사전 등록 효과

- 5,000종 전체 분류 → 사용자 등록 N종 풀에서 매칭
- 정확도 본질적 향상

### 4.2 하드웨어 보강

- **MVP**: 안드로이드 S24 폰 카메라로 미세 각인 인식 (컬러 정보 활용 가능)
- **확장**: pylon 고해상도 산업 카메라 + Ring Light로 정확도 추가 보강

> 참고: 360도 회전 거치대(양면 촬영)는 본 프로젝트 범위 외. 거울/지그재그 거치 대안은 추후 검토.

### 4.3 신뢰도 단계 메시지

- 95% ↑ / 70~95% / 70% ↓ 3단계 분기
- 사용자에게 정확한 신호 전달

### 4.4 표현 톤

- 모든 결과 "추정" 톤
- "식약처 DUR 인용" 표기 (또는 "DUR 등록 확인되지 않음" 표기)
- "약사·의사 상담 권유" 일관
- ⭐ **단정 문구 금지** — "복용 가능합니다 / 불가합니다" 등 표현 사용 X
- 안전 케이스도 단정 X — "DUR 등록 확인되지 않음 + 상담 권유" 톤으로 통일

### 4.5 LLM·RAG 활용 영역 제한 ⭐

- ✅ **사용 OK**: YOLO26 (검출), PaddleOCR (OCR), 폰 온디바이스 STT (Galaxy AI / Android `SpeechRecognizer`)
    - 변환·인식 AI는 의료 정보 창작 X
- ❌ **사용 금지 (의료 안내 영역)**: GPT/Claude 등 LLM이 DUR 위험 안내·진단성 응답을 자연어로 창작·변환. **RAG 도입 시에도 의료 안내 영역에는 절대 미적용**
    - 환각·왜곡으로 인한 잘못된 의료 안내의 법적 리스크 차단
- 🔶 **활용 (등록·일반 안내·의도 분류 보조 역할에 한정, RAG 허용)**:
    - **약 정보 등록(Onboarding) 단계** (RAG 허용): 폰 STT 결과의 약명 추출·정규화, 직접 입력 시 모호한 약명에 대한 후보 추천, 동명·동성분 약 분기 질문 생성, 등록 확인 단계의 e약은요 자연어 요약을 통한 사용자 이해 보조
    - **의도 분류기 역할 (일상 사용 단계)**: 폰 STT가 텍스트로 변환한 사용자 발화의 카테고리만 분류 (약 식별 요청 / 위험 점검 요청 / 단순 정보 확인 / 등록 요청 / 복약 이력 조회 / 보고서 출력 / 기타). 분류 후엔 시스템이 정해진 흐름을 탐. **응답 생성·의료 안내 영역에는 진입 ❌**
    - **비의료 일반 안내 보조** (RAG 허용): e약은요의 비위험 정보(효능·복용법 등) 자연어 요약
    - **능동/대화형 가이드 트리거**: 정보 부족 시 "카메라로 약을 비춰주세요", 인식 결과에 따라 "약을 눕혀주세요" 등 일반 안내 멘트 생성 (의료 정보 창작 X)
- ❌ **외부 인터넷 출처 사용 금지**: 약 조합 위험 정보는 식약처 DUR/e약은요 데이터만 사용. 외부 블로그·논문·인터넷 검색 결과 사용 X — 법적·의료적 책임 소재 불분명

## 5. 시스템 운용 안정성 (인프라 관점)

> 4장의 "다층 안전 메커니즘"이 의료 안전성 관점이라면, 본 장은 시스템 자체의 안정적 운용·가용성 관점.

### 5.1 자원 모니터링

- 운용 서버 PC와 추론 PC의 CPU·메모리·GPU 사용량 실시간 모니터링
- 추론 PC의 모델 로딩/언로딩 전략, 추론 배치 사이즈 관리
- 각 PC의 리소스 한도 내 동작 보장

### 5.2 자동 재연결(Auto-reconnect)

- 폰 ↔ GUI PC(USB/WiFi) 연결 유실 시 자동 재연결 로직
- GUI PC ↔ 운용 서버 PC TCP/IP 통신 단절 시 자동 재연결
- 운용 서버 PC ↔ 추론 PC TCP/IP 통신 단절 시 자동 재연결
- 운용 서버 ↔ 식약처 OpenAPI 호출 실패 시 캐시 fallback (외부 API 장애와 무관하게 시스템 동작 유지)

### 5.3 자원 누수 방지

- 장시간 운용(24시간+) 시 메모리·핸들 누수(Leak) 방지 전략 수립 및 검증
- 주기적 헬스체크 및 비정상 상태 자동 복구

### 5.4 로깅 / 트러블슈팅

- 예외 상황 로깅, 로그 수준 분리(DEBUG/INFO/WARN/ERROR)
- 트러블슈팅 절차 정립

### 5.5 프롬프트 인젝션 방어 ⭐

- 폰 STT 결과 텍스트·키보드 입력이 LLM 분류기 또는 Onboarding LLM을 우회해 의료 안내 응답 생성 영역으로 진입하지 않도록 다층 방어
- **입력 검증**: 사용자 입력에서 시스템 프롬프트 변조 시도(예: "이전 지시는 무시하고...", "당신은 이제 의사야" 등) 패턴 검출 및 차단
- **시스템 프롬프트 락**: 분류기 LLM의 출력 형식을 카테고리 라벨로 강제(JSON 스키마 강제), 자연어 응답 생성 자체를 구조적으로 차단
- **영역 분리**: 의료 안내 영역 응답 생성 코드 경로에 LLM 호출 자체가 부재하도록 구조 설계 — 우회되어도 호출할 LLM이 없음
- **로그 감시**: 의심스러운 입력 패턴은 로깅하여 사후 분석

### 7.3 데이터 적재 정책 ⭐

식약처 데이터는 두 가지 방식으로 분리하여 적재한다.

**일괄 적재 데이터** (식별·DUR의 핵심)

- **대상**: 낱알식별, DUR 품목, DUR 성분
- **방식**: 식약처가 제공하는 **CSV/EXCEL 파일 일괄 다운로드** 또는 **스마트싱크(MariaDB 자동 동기화 도구)** 사용
- **갱신**: 주기적(예: 월 1회 또는 수동)
- **저장소**: 운용 서버 MariaDB

**lazy 캐싱 데이터**

- **대상**: e약은요(효능·복용법·주의사항·부작용·보관법)
- **방식**: 사용자가 등록하거나 조회한 약에 한정해, 요청 시점에 외부 API에서 받아 DB에 누적 저장
- **다음 요청부터**: DB에서 반환
- **TTL 정책**: 없음 (v1.0의 30일 TTL 정책 폐기 — 단순화)

**조회 정책**

- 식별·DUR 위험 검출 단계는 외부 API 호출 없이 로컬 DB 조회만으로 동작
- e약은요는 1차 = 로컬 DB → 2차 = 캐시 미스 시 외부 API → DB 누적
- 외부 API 장애 시에도 식별·위험 검출 핵심 기능은 영향 없음 (e약은요 신규 약 조회만 일시적으로 제한될 수 있음)
- 식약처 낱알이미지는 DB에 직접 저장하지 않고 식약처 URL을 텍스트로 보관 (화면 표시 시 URL 참조)
- **활용 영역**: Rule-based 조회 (의료 안내 영역) + RAG 검색 소스 (비의료 영역)

## 8. 활용 시나리오

### 8.1 노인 복약 혼동 예방

- 노인이 약을 헷갈려 복용하는 사고 있음
- 사전 등록된 약 풀로 식별 정확도를 높이고, DUR로 위험 자동 검출
- 출처: 팀원 지인의 요양원 근무 경력 청취

### 8.2 요양원·병원 투약 전 최종 체크 (확장 단계)

- 다수 환자의 알약을 투약하기 전 일괄 검수
- 간호사·요양보호사 반복 작업 자동화

### 8.3 일반의약품 자가 구매 시 안내 누락 보완

- 동일 약국에서 진통제+감기약 동시 구매: 약사가 동일 성분 중복(아세트아미노펜) 안내
- 다른 약국·다른 시점 별도 구매: 안내 누락
- 사용자가 모든 약을 등록해두면 시스템이 DUR로 자동 검출

### 8.4 의사 상담 시 통합 보고서 출력 (모듈 5 — MVP 시나리오)

- 사용자가 복용한 약의 종류·개수·이름·복용 시각을 보고서로 출력해 의사·약사에게 제출
- 약별 부작용 주요 증상은 식약처 e약은요 데이터(주의사항·부작용 항목)에서 인용한 형태로 표시 — LLM 자연어 생성 미사용
- 인쇄 또는 PDF 형태 — 진료 효율과 안전성 동시 향상

### 8.5 사용자 인증 + 복약 이력 기록 (모듈 6 + 모듈 2 — MVP 시나리오)

- 사용자가 회원가입 후 로그인하여 자신의 약 풀과 복약 이력을 분리 관리
- 알약 식별 후 "복용 기록을 남기시겠습니까?" 흐름으로 자동 연결 — 복용 시각(분 단위)·약 이름·개수·메모 기록
- 일자별·약별·기간별 필터로 복약 이력 조회 가능

### 8.6 헬스케어 데이터 통합 보고서 (확장 시나리오)

- 핸드폰 건강 데이터(심박수·걸음수·수면 시간)를 복약 이력과 함께 통합 보고서에 표기
- 본 프로젝트 범위 외 — 모듈 4(헬스케어 데이터 연동)가 확장 범위

## 10. 본 프로젝트 범위 외 — 추후 검토 사항

> 학생 포트폴리오 범위로 한정. 다만 사업화·확장 단계에서 다음 검토.

### 10.1 의료·신뢰성

- 병원·약국과 협업한 안전성 검증 (사용자 테스트, 약사 평가, 임상 시범)
- 유관 단체 자문 (대한약사회, **환자안전약물관리원** — 대한약사회 산하, **한국의약품안전관리원(KIDS)** — 식약처 산하 공공기관)
- 긴급 연결 라인 구축 (119, 1339 응급의료상담, 약사 직통)
- 정식 의료기기 인증 (식약처, ISO 13485, GMP)

### 10.2 하드웨어 확장

- **Basler pylon 산업 카메라 도입** — MVP 정확도 부족 시 진입. 컬러 미지원(모노크롬) 가능성 있어 색상 매칭 fallback 설계 필요
- **양면 촬영 대안** — 거울 / 지그재그 거치 (Arduino 회전 거치대 대비 저비용·저공간)
- **Arduino 부저/LED 알림** — 위험 검출 시 청각·시각 신호

### 10.3 기능 확장 (메디브릿지 플랫폼)

**확장 모듈**

- **모듈 3 (증상 / 부작용 기록)** — 사용자가 느낀 증상을 텍스트·음성으로 기록, 복용 시각과 매칭하여 의료진의 인과 추정 보조
- **모듈 4 (헬스케어 데이터 연동)** — 핸드폰 건강 데이터(심박·걸음·수면) 수집 + 보고서 통합

**모듈 2 (복약 이력) 확장**

- 음성 → 복약 이력 자동 기록 ("타이레놀 2알 먹었어" → 폰 STT → LLM 추출 → DB 저장)
- 음성 → 복약 이력 자연어 조회 ("어제 먹은 약 뭐야?" → DB 조회 + 템플릿 출력)
- 복약 알림·리마인더 — 시각 알람, 미복용 알림

**모듈 5 (통합 보고서) 확장**

- 가족·간병인 공유 — 보호자가 환자 복약 상태 모니터링
- 약사·의료진 연계 — 보고서 전자 전송, 표준 양식

**모듈 1 (알약 식별) 확장**

- 단일 촬영 등록 (Top-N 후보 → 사용자 선택)
- DUR 위험 카테고리 ②~⑧ 확장
- 등록 풀 정확도 모니터링 — 등록 약 풀 크기에 따른 매칭 정확도 자동 모니터링 + 임계 초과 시 정리 안내 (MVP는 사용자 수동 리셋만 제공)
- **STT fallback** — 폰 온디바이스 STT 정확도 부족 시 추론 PC Whisper로 자동 fallback 또는 비교 평가

**기타**

- 자유 대화 컨텍스트 유지 (멀티턴 챗봇) — 의료 안내 영역 진입 위험 통제와 함께 별도 설계 필요

### 10.4 배포 환경

- **모바일 배포** — 안드로이드 우선 (iOS는 보안 체계상 외부 카메라·외부 통신 제약 큼). 추론 모델 경량화 및 온디바이스 추론 비용 효율성 검증 필요
- 라즈베리파이 / AWS

> 다음 항목은 본 프로젝트 범위에서 명시적으로 제외:
> - 동일 성분 시간차 누적 카운팅 (약물동력학 기반 자동 차단) — 의료적 판단 영역에 가까워 본 프로젝트 범위 외

## 12. 가명화 정책 (PIPA·GDPR 대응) ⭐ v3.0 신규

> 정본: [DB ERD v4](DB_ERD_ver4.md), [시스템_연결구조 v2.2 §8](시스템_연결구조_ver2.md)

### 12.1 단일 끊기 매핑 원칙

```
[ users (user_id, email, name) ]
        │
        │ user_id (이 한 줄만 끊으면 익명화 완료)
        │
[ pseudonym_map (anonymous_id, user_id ⭐, severed_at) ]
        │
        │ anonymous_id (4곳 사용)
        ├─ user_medication_pool
        ├─ medication_intake_logs
        ├─ user_reports
        └─ photo_storage
```

모든 데이터 테이블에서 `user_id` FK 를 제거하고 `anonymous_id` 로 교체. user 와 anonymous 매핑은 `pseudonym_map` 단일 테이블에만 존재.

### 12.2 익명화 SQL (1년 경과 매핑 끊기)

```sql
UPDATE pseudonym_map
   SET user_id = NULL, severed_at = NOW()
 WHERE created_at < NOW() - INTERVAL 1 YEAR
   AND user_id IS NOT NULL;
```

→ 사진·이력·보고서는 그대로 보존, user 추적만 차단. systemd timer 일 1회 실행 권장.

### 12.3 PII 컬럼 분류

| 분류 | 컬럼 | 익명화 후 처리 |
| --- | --- | --- |
| 직접 식별자 (`users`) | email, password_hash, user_name | 사용자 탈퇴 시 행 삭제 또는 별도 정책 |
| 가명 식별자 | `pseudonym_map.user_id` | **본 정책의 핵심 끊기 대상** |
| 자유 텍스트 PII 가능 | `medication_intake_logs.memo`, `user_reports.report_notes` | 끊기 시 NULL 처리 |
| 사진 파일명 | `<anonymous_id>_<photo_id>.jpg` | 자체로 비식별 |
| 음성 STT 원본 텍스트 | 메모리에서만 처리, DB 저장 X | 영구 비저장 |
| 음성 → 추출 구조화 (약명·개수) | 정상 보관 | 자유 텍스트 마스킹과 동일 |

## 13. Onboarding RAG round-trip ⭐ v3.0 신규

> 정본: [PillApi v0.3 §3](Api/PillApi.md#3-post-v1pillonboardingnormalize), [시스템_연결구조 v2.2 §2.8](시스템_연결구조_ver2.md)

사용자가 의료용어를 모르는 상태에서 음성으로 약 등록 시 (예: "빨간 알약 진통제 등록할게"), 식약처 의약품 RAG 로 약명·성분 후보 추출 + 동명·동성분 분기 질문 round-trip 다회 반복.

| 단계 | 흐름 |
| --- | --- |
| 1 | 폰 STT → 클라 PC → 메인 서버 `POST /v1/pill/onboarding/normalize` |
| 2 | 메인 서버 → LLM PC 10.10.10.120 (NER + ChromaDB 벡터 검색) |
| 3 | state 분기: `RESOLVED` (1건) / `NEED_DISAMBIGUATION` (2~5건) / `NOT_FOUND` |
| 4 | TTS 안내 (§14) → 사용자 응답 → round=k+1 재호출 |
| 5 | RESOLVED + 사용자 OK → `POST /v1/pill/pool` |

**남용 방어**: `max_rounds=5`, `max_input_tokens=200`, rate limit. **stateless** (`prev_choice_token` 으로 컨텍스트 복원).

## 14. TTS 어댑터 정책 ⭐ v3.0 신규

> 정본: [시스템_연결구조 v2.2 §2.9](시스템_연결구조_ver2.md), [프로토콜 v2.1 §3.3](프로토콜_ver2.md)

| 방식 | 데이터량 (안내 1회) | 장점 | 단점 |
| --- | --- | --- | --- |
| **클라 자체 TTS (MVP 기본)** | 텍스트만 (~수백 B) | 무료, 지연 0 | 음질 OS 의존 |
| 메인 서버 TTS (MP3 96kbps, fallback) | 60~180KB | 자연 음질 | 클라 대비 100~300배 트래픽, 클라우드 비용 |

```
ITtsProvider {
    speak(text, language) -> void
    cancel() -> void
    is_available() -> bool
}
구현: QtSpeechProvider (기본) / PhoneTtsProvider (옵션) / ServerTtsProvider (fallback)
```

Fallback 발동: `is_available()==false`, "고품질 음성" 사용자 설정, 메인서버 TTS 실패 시 이중 fallback.

## 16. 인증 — PBKDF2-SHA256 + HS256 JWT ⭐ v3.0 실 구현

> 정본 코드: `MainServer/Services/Auth/{PasswordHasher,JwtIssuer,Authenticator,UserManager}.cpp`

| 컴포넌트 | 알고리즘 | 라이브러리 |
| --- | --- | --- |
| PasswordHasher | PBKDF2-SHA256 (100k iter / 16B salt / 32B hash) | OpenSSL `EVP_PBKDF2` |
| JwtIssuer | HS256 (header.payload.signature, RFC 7519) | OpenSSL `HMAC` |
| Authenticator | find_by_email + verify + issue 조합 | — |
| UserManager | 실 DB CRUD (prepared statement 바인딩) | Drogon ORM |

→ jwt-cpp / libbcrypt 등 추가 의존성 X (OpenSSL 만 사용). 시드 사용자(`$pbkdf2$test_hash_placeholder$<plain>`) 도 development 환경에서 통과, production 에서는 거부.
