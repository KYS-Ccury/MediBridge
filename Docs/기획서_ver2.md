> **메디브릿지(MediBridge)**: 환자와 의료진을 잇는 다리. 알약 식별·복약 이력·증상 기록·헬스케어 데이터·통합 보고서로 구성되는 복약·건강 통합 케어 플랫폼. 본 프로젝트는 그중 **모듈 1(알약 식별 + 안전 점검)** 을 중심으로, 모듈 2(복약 이력), 모듈 5(통합 보고서), 모듈 6(인증)을 함께 구현한다.

> ⭐ **v2.0 변경 핵심**: ① 통신 ① (GUI↔운용 서버) 표기를 「TCP/IP (REST API on HTTP) + 미디어/텍스트 별도 엔드포인트」로 명문화. ② 입력 디바이스를 「안드로이드 S24 폰 (카메라 + 마이크 + 온디바이스 STT)」으로 통합 명시. ③ 6장 시스템 아키텍처 그림에서 추론 PC의 Whisper STT를 「확장 fallback」으로 분리. ④ 8장 어필 포인트에 「폰 온디바이스 STT를 통한 대역폭·개인정보 이중 최적화 의사결정」 추가.

### 1.1 메디브릿지 플랫폼 모듈 구조

메디브릿지는 6개 모듈로 구성되는 통합 플랫폼이다. 본 프로젝트(MVP)는 모듈 1·2·5·6을 우선 구현하고, 모듈 3·4 및 추가 확장은 추후 단계에서 진행한다.

| # | 모듈 | 본 프로젝트 (MVP) | 비고 |
| --- | --- | --- | --- |
| **1** | **알약 식별 + 안전 점검** | ✅ 핵심 | YOLO26·PaddleOCR·OpenCV·LLM·식약처 DUR. 사전 등록 약 풀 기반. 본 기획서의 무게중심 |
| **2** | **복약 이력 관리** | ✅ 포함 | 복용 시각·약·개수·메모. 일자별·약별 조회 |
| **3** | 증상 / 부작용 기록 | ⚠️ 확장 | 사용자가 느낀 증상을 텍스트·음성으로 기록. 복용 시각과 매칭하여 의료진 인과 추정 보조 |
| **4** | 헬스케어 데이터 연동 | ⚠️ 확장 | 핸드폰 심박·걸음·수면·활동량 (Health Connect / HealthKit) |
| **5** | **통합 보고서** | ✅ 포함 (공통 인프라) | 의사 상담용 인쇄/PDF. MVP는 약 정보 + 복약 이력 + 식약처 부작용 인용. 확장에서 모듈 3·4 데이터 추가 |
| **6** | **사용자 계정 / 인증** | ✅ 포함 (공통 인프라) | 회원가입·로그인. 모듈 간 사용자 데이터 통합 |

### 1.2 확장 로드맵 (본 프로젝트 범위 외)

- **음성 → 복약 이력 자동 기록** — "타이레놀 2알 먹었어" 발화 → 폰 STT → LLM 추출(약명·개수·시각) → 복약 이력 DB 자동 저장
- **음성 → 복약 이력 자연어 조회** — "어제 먹은 약 뭐야?" → DB 조회 + 정해진 템플릿 출력
- **복약 알림·리마인더** — 시각 알람, 미복용 알림
- **가족·간병인 공유** — 보호자가 환자 복약 상태 모니터링
- **약사·의료진 연계** — 보고서 전자 전송, 표준 양식
- **자유 대화 컨텍스트 유지** (멀티턴 챗봇) — 의료 안내 영역 진입 위험 통제와 함께 별도 설계 필요

## 2. 시스템 요구사항

> 프로그램 요구사항과 포함 기술 요소를 통합 정리

### 2.1 통합 시스템 구성

- **머신비전 통합 시스템**으로 구축
- 다음 요소를 **모두 활용**해야 함
    - **서버** (학습 서버 / 운용 서버 **분리** 구성, 본 프로젝트는 **GUI PC + 운용 서버 PC + 추론 PC + 학습 서버 4대 분리** 구성으로 확정 — 시스템 흐름 정리본 v2 2.1장 참조)
    - **TCP/IP** 통신 (GUI PC ↔ 운용 서버, 운용 서버 ↔ 추론 PC 두 구간에서 활용. **두 구간 모두 REST API(HTTP) 위에서 동작**. 통신 ①은 미디어(이미지)·STT 텍스트를 별도 엔드포인트로 분리)
    - **DB** (운용 서버 MariaDB 단일 — 사용자 계정(모듈 6) + 사용자별 약 풀(모듈 1) + 복약 이력(모듈 2) + 식약처 데이터)
    - **GUI 애플리케이션 Qt/C++** (본 프로젝트는 **Qt6 + C++ + QML**로 확정. 기능 단위 모듈 분리)
    - **AI 모델 (트랜스포머, CNN)**
- **개발 ~ 배포**까지의 전 과정 경험 확보

### 2.2 AI / 알고리즘

- **머신비전** (CNN 기반 모델 등)
- **LLM·RAG 활용은 영역을 제한**해 적용
    - **의료 안내(DUR 위험 안내, 진단성 응답) 영역에는 LLM·RAG 모두 미사용** — 환각·왜곡으로 인한 의료 정보 오류 리스크 차단. 식약처 DUR 데이터를 정해진 템플릿으로만 출력
    - **약 정보 등록(Onboarding) 단계** ✅ RAG 허용: 음성 인식 등록 시 **폰 STT 결과의 약명 추출·정규화**, 직접 입력 시 모호한 약명에 대한 후보 추천, 등록 시 동명·동성분 약 후보 분기 질문 생성, 등록 확인 단계에서 e약은요 정보 자연어 요약 등
    - **일상 사용 시 의도 분류기 (Stage 0.5)**: 사용자 음성 발화의 카테고리만 분류 (응답 생성 X). 분류 결과에 따라 시스템이 정해진 흐름으로 라우팅
    - **비의료 일반 안내 보조** ✅ RAG 허용: e약은요의 비위험 정보(효능·복용법 등) 자연어 요약. **단, DUR 위험 안내 영역에는 절대 사용 안 함**
    - 외부 지식 데이터(External Knowledge Sources)는 식약처 데이터 4종을 **로컬 DB 적재 + Rule-based 조회**로 동작. 식별·DUR의 핵심 데이터(낱알식별·DUR 품목·DUR 성분)는 식약처 CSV/EXCEL 또는 스마트싱크(MariaDB 자동 동기화)로 일괄 적재. e약은요(효능·복용법)는 사용자 요청 시점에 lazy 캐싱(만료 정책 없음). 비의료 영역에서는 RAG 활용 가능. 의료 안내 영역의 LLM 응답 생성 구조는 채택하지 않음
    - LLM Agent 오케스트레이터는 **등록·의도 분류·일반 안내 보조 역할에 한정**, 의료 안내 영역의 자율 호출·응답 생성 ❌
    - **외부 인터넷 출처 사용 금지**: 약 조합 위험 정보는 식약처 DUR/e약은요 데이터만 사용. 외부 블로그·논문·인터넷 검색 결과 사용 X (법적·의료적 책임 소재 불분명)
    - **프롬프트 인젝션 방어**: 사용자 음성·텍스트 입력이 LLM 분류기·Onboarding LLM을 우회해 의료 안내 영역으로 진입하지 않도록 입력 검증·시스템 프롬프트 락 적용
    - **표현 톤 — 단정 문구 금지**: "복용 가능합니다 / 불가합니다" 등 단정 표현 사용 X. 안전 케이스도 "DUR 등록 확인되지 않음 + 약사·의사 상담 권유" 톤으로 통일

### 2.3 시스템 안정성 및 가용성

- **추론 성능**: 속도와 정확도 확보
- **메모리 / 자원 관리**: 좁은 의미의 C/C++ 메모리 관리뿐 아니라, **실제 운용 환경에서 메모리 사용량을 모니터링·제어하여 시스템이 안정적으로 동작하도록 하는 포괄적 자원 관리**를 목표로 함
    - 모델 로딩/언로딩 전략
    - 추론 배치 사이즈 관리
    - 운용 서버의 리소스 한도 내 동작 보장
- **가용성 설계 (현장 중심)**
    - 단순 동작을 넘어 **산업 현장의 가동률**을 고려한 '무중단 서비스' 지향 아키텍처
    - 시스템 리소스(CPU/메모리) **실시간 모니터링** 및 상태 감시 로직
    - **외부 API 의존 최소화** — 식약처 데이터를 MariaDB에 일괄 적재(CSV/스마트싱크)하여 운용 중에는 외부 API 호출이 거의 발생하지 않음. 외부 API 장애 시에도 시스템 동작 가능
- **장애 복구 및 장기 운용 안정성**
    - **폰 ↔ GUI PC** 연결 유실 / 네트워크 불안정 시 **자동 재연결(Auto-reconnect)** 프로세스
    - 장시간 운용 시의 **자원 누수(Leak) 방지** 전략 수립 및 검증
    - 예외 상황 로깅 및 트러블슈팅 절차 정립

### 2.4 하드웨어 / 인터페이스

- **MVP 입력 디바이스**: **안드로이드 S24 폰** (GUI PC에 USB 직결 또는 WiFi 전송) — 카메라 + 마이크 + **온디바이스 STT(Galaxy AI / Android `SpeechRecognizer`)** 를 모두 처리. 일반 환경에서 컬러 정보 활용 가능, 검증·반복 테스트 부담 낮음, **음성 바이너리가 서버 구간에 흐르지 않아 대역폭 절감 + 개인정보 노출 위험 감소**
- **확장 카메라**: **Basler pylon (상업용 산업 카메라)** — MVP 정확도가 부족할 경우 도입. GUI PC USB 직결, pylon SDK 활용. ⚠️ 컬러 미지원(모노크롬) 가능성 — 도입 시 색상 매칭 fallback 설계 필요
- **확장 STT fallback**: 폰 온디바이스 STT 정확도 부족 시 추론 PC의 Whisper STT(`POST /speech/stt`)로 음성 바이너리 송신 fallback 경로 활성화
- **아두이노**: **본 프로젝트 미사용**으로 결정.
    - 회전 거치대(Stepper Motor)는 1년에 수회 사용되는 기기 특성상 가격·공간 부담 대비 효용이 낮아, 양면 촬영은 단면 촬영 + 사용자 가이드(앞뒷면 뒤집기)로 대체
    - 부저/LED 알림은 본 프로젝트 범위 외(추후 검토 사항)
    - ⚠️ **교수 컨펌 시 "아두이노 활용" 요구사항 충족 여부 재확인 필요** (필요 시 다른 형태로 충족하거나 요구사항 조정)
- **라즈베리파이**: 보유 미확인 → MVP에서는 미사용. **보류 → 추후 결정** (필요 시 사전 요청)
- **AWS**: MVP는 로컬 서버 구성. **보류 → 추후 결정** (사업화·확장 단계에서 검토)

### 2.5 데이터 접근 원칙

- 항상 **'데이터부터 찾고'** 그에 맞는 모델을 선정
- 사유: 데이터 확보가 가장 큰 병목 (프로젝트 기간이 짧음)

### 2.6 인증·복약이력·보고서 (모듈 2 / 5 / 6)

본 프로젝트 MVP에서는 모듈 1(알약 식별)과 함께 다음 모듈들을 구현한다.

- **모듈 6 (사용자 계정 / 인증)**: 회원가입·로그인으로 사용자별 약 풀과 복약 이력을 분리 관리. 비밀번호는 bcrypt 등 표준 해시로 저장. 세션/토큰(JWT 등) 발급. 모든 약 풀·복약 이력 API는 인증된 사용자에 한해 본인 데이터만 접근. 파라미터 바인딩으로 SQL 인젝션 방어
- **모듈 2 (복약 이력 관리)**: 사용자가 약 복용 시 복용 시각(년·월·일·시·분)·약 이름·개수·메모를 기록. 시각 미입력 시 시스템 시각 자동 사용. 일자별·약별·기간별 필터로 조회. 시각은 분 단위까지 저장되어 아침/점심/저녁/취침 자동 분류 가능. 식별 신뢰도·DUR 스냅샷도 선택적으로 함께 저장
- **모듈 5 (통합 보고서)**: 지정 기간의 복약 이력을 표 형태로 출력. 약별 부작용 주요 증상은 식약처 e약은요 데이터(주의사항·부작용 항목)에서 인용한 형태로 표시(LLM 자연어 생성 미사용). 인쇄 또는 PDF 출력으로 의사·약사에게 제출 가능

## 3. 진행 절차 및 자원 요청

- 시스템 주제는 **컨펌을 받고** 진행할 것
- 필요한 자원은 **사전에 요청**
    - **안드로이드 S24 폰** (개인 보유분 활용 가능 여부 + GUI PC 연결 케이블/소프트웨어 환경 준비)
    - PC 4대 분리 구성 가능 여부 확인 (GUI PC + 운용 서버 PC + 추론 PC + 학습 서버) — 환경 구성 부담 큼

## 5.2 활용 시나리오 (선정 아이템 기준)

**타깃 사용자**: 주 타깃 노인층 + 보조 타깃 청·장년층 (유니버설 디자인)

1. **[주 타깃] 노인 복약 혼동 예방** — 사전 등록된 약 풀로 식별 정확도 향상 + DUR로 위험 자동 검출. 음성 인터페이스 기반 쉬운 접근성 (MVP 시나리오)
2. **[주 타깃] 요양원·병원 투약 전 최종 체크** — 다수 환자 알약을 투약 전 일괄 검수, 간호사·요양보호사 반복 작업 자동화 (확장 시나리오)
3. **[주 타깃] 일반의약품 자가 구매 시 안내 누락 보완** — 다른 약국·다른 시점에 별도 구매한 약의 동일 성분 중복(예: 아세트아미노펜)을 자동 검출 (MVP 시나리오)
4. **[보조 타깃] 청·장년층의 체계적 복약 관리** — 처방약·일반의약품·영양제 등 다양한 약 동시 복용 시 사전 등록 후 자동 DUR 점검, 음성 질문으로 신속한 정보 확인 (MVP 시나리오)
5. **[모듈 5 — MVP] 의사 상담 시 통합 보고서 출력** — 사용자가 복용한 약의 종류·개수·이름·복용 시각을 보고서로 출력해 의사·약사에게 제출. 약별 부작용 주요 증상은 식약처 e약은요 데이터에서 인용. 인쇄 또는 PDF 형태 (MVP 시나리오)
6. **[확장] 음성으로 복약 이력 기록** — "타이레놀 2알 먹었어" 발화 → 폰 STT → LLM 추출 → 복약 이력 DB 자동 저장 (확장 시나리오)
7. **[확장] 헬스케어 데이터 통합 보고서** — 핸드폰 건강 데이터(심박수·걸음수·수면)를 복약 이력과 함께 통합 보고서에 표기 (확장 시나리오)

## 6. 시스템 아키텍처 (초안)

> LLM·RAG는 등록 단계 + 일상 사용 의도 분류 + 비의료 일반 안내 보조에 한정. 의료 안내 영역(DUR 위험 안내)에는 미사용. 식약처 데이터는 CSV/스마트싱크로 MariaDB에 일괄 적재 + e약은요 lazy 캐싱(만료 정책 없음). 1차 조회는 로컬 DB 우선. **MVP STT는 폰(S24) 온디바이스 처리**, 추론 PC Whisper는 확장 fallback. 시스템 상세는 「시스템 흐름 정리본 v2」 2.1장 참조.

```
        안드로이드 S24 폰 (MVP) / pylon(확장)
        ─ 카메라 (다중 알약 촬영)
        ─ 마이크 + 온디바이스 STT
          (Galaxy AI / SpeechRecognizer)
            │ USB 또는 WiFi
            │ (이미지 + STT 텍스트)
            ▼
   ┌── ① GUI PC ────────────────────────────────┐
   │ Qt6 + C++ + QML GUI                        │
   │ (기능 단위 모듈 분리:                      │
   │  폰 입력 수신 / 결과 표시 /               │
   │  사용자 입력 +                            │
   │  로그인·회원가입(모듈 6) /                │
   │  복약 이력(모듈 2) /                      │
   │  통합 보고서(모듈 5))                     │
   │ + TTS 출력 (능동/대화형 가이드 등)        │
   └────────────────────────────────────────────┘
        │ TCP/IP (REST API on HTTP)
        │  + 미디어/STT 텍스트 별도 엔드포인트
        ▼
   ┌── ② 운용 서버 PC ─────────────────────────────┐
   │ FastAPI                                       │
   │ + DB (MariaDB) ← 메인 DB                       │
   │   ├ 사용자 계정 (모듈 6 — 인증)               │
   │   ├ 사용자별 약 풀 (모듈 1)                   │
   │   ├ 복약 이력 (모듈 2)                        │
   │   └ 식약처 데이터 (낱알식별·DUR·e약은요)      │ ◄── HTTPS ──► 식약처 OpenAPI
   │     (CSV/스마트싱크 일괄 적재 +                │       (e약은요 lazy 캐싱 시에만)
   │      e약은요 lazy 캐싱, TTL 없음)              │
   │ + 모듈 1: 위험 안내 템플릿 (LLM·RAG 미사용)   │
   │ + 모듈 2: 복약 이력 기록·조회 API             │
   │ + 모듈 5: 통합 보고서 생성                    │
   │ + 모듈 6: 회원가입·로그인·세션/토큰 관리      │
   │ + 프롬프트 인젝션 방어 레이어                 │
   └───────────────────────────────────────────────┘
        │ TCP/IP (REST API on HTTP)
        ▼
   ┌── ③ 추론 PC (GPU) ──────────────────────────────┐
   │ YOLO26 + PaddleOCR + OpenCV (Vision)           │
   │ + (확장 fallback) Whisper (STT)                 │
   │ + LLM 의도 분류기 (Stage 0.5, 분류만)          │
   │ + LLM·RAG 등록·일반 안내 보조 (한정)           │
   └────────────────────────────────────────────────┘
        ▲
        │ 모델 배포 (SCP/파일 전송, 운용 시엔 통신 없음)
        │
   ┌── ④ 학습 서버 (별도) ──┐
   │ 데이터 수집 → 학습      │
   └─────────────────────────┘
```

> **요약**: 학습 서버 / 운용 서버 / 추론 PC / GUI PC **4대 분리** + **안드로이드 S24 폰 입력 디바이스**. TCP/IP는 GUI ↔ 운용 서버, 운용 서버 ↔ 추론 PC 두 구간에서 활용 (둘 다 REST API on HTTP). 통신 ①은 미디어(이미지)·STT 텍스트를 별도 엔드포인트로 분리. **음성은 폰의 온디바이스 STT로 클라이언트 측에서 텍스트 변환**, 추론 PC Whisper STT는 확장 fallback. 식약처 데이터는 CSV/스마트싱크로 MariaDB에 일괄 적재 + e약은요는 lazy 캐싱(만료 없음). 운용 서버 PC가 인증(모듈 6)·복약 이력(모듈 2)·통합 보고서(모듈 5) 모듈을 함께 호스팅. Arduino는 본 프로젝트 미사용.

## 8. 포트폴리오 어필 포인트

> 본 섹션은 **대외 포트폴리오 자료용**. 면접 답변용 메시지는 「시스템 흐름 정리본 v2」 11장 참조.

- **실무형 시스템 설계**: 단순 모델링이 아닌, 인프라 관점에서 **서비스 가용성을 최우선**으로 고려한 안정적인 End-to-End 시스템 구축 경험
- **자원 최적화 역량**: 하드웨어 리소스 한도 내에서 최적의 추론 성능을 유지하기 위한 **모델 및 자원 관리 실무** 경험
- **통합 엔지니어링 경험**: 데이터 수집(HW)부터 AI 추론, 결과 시각화, 배포까지 이어지는 **전체 파이프라인 협업** 역량
- **문제 해결 데이터 확보**: 로그 분석과 예외 상황 트러블슈팅을 통해 **시스템 신뢰성을 검증**한 과정
- **신중한 LLM·RAG 적용 — 영역별 분리 설계**: 의료 안내 영역에는 LLM·RAG를 사용하지 않고 정해진 템플릿으로만 출력. 비의료 영역(약 정보 등록·일반 안내)에 한해 RAG 활용 — **법적·윤리적 리스크 인식 기반의 영역별 의사결정** 경험
- **외부 인터넷 출처 차단 + 프롬프트 인젝션 방어**: 식약처 데이터 외 외부 인터넷 출처 사용 금지 정책, 사용자 입력의 우회 방지 입력 검증·시스템 프롬프트 락 적용 — **보안·안전 설계 의사결정** 경험
- **외부 API 의존 최소화 — 일괄 적재**: 식약처 데이터(낱알식별·DUR 품목·DUR 성분)를 CSV/스마트싱크로 MariaDB에 일괄 적재, e약은요는 사용자 요청 시점에 lazy 캐싱(만료 정책 없음) — 운용 중 외부 API 호출 거의 없음, 외부 API 장애 시에도 시스템 동작 보장 — **운영 안정성 설계** 경험
- ⭐ **(v2.0 신규) 폰 온디바이스 STT — 대역폭·개인정보 이중 최적화**: 안드로이드 S24의 내장 AI(Galaxy AI / `SpeechRecognizer`)로 음성을 클라이언트 측에서 텍스트 변환 후 송신. 운용 서버·추론 PC 구간에 음성 바이너리가 흐르지 않아 **트래픽 수백~수천 배 감소 + 음성 원본 비저장(개인정보 보호)** 동시 달성. 정확도 부족 시 추론 PC Whisper로 fallback 가능한 어댑터 구조 — **클라이언트/서버 책임 분담의 트레이드오프 의사결정** 경험
- **음성 + 카메라 멀티모달 인터페이스**: 노인층 친화 음성 인터페이스(폰 STT/TTS) + 카메라 입력을 결합. LLM은 의료 안내 영역에는 진입하지 않고 분류기·등록·일반 안내 보조 역할에 한정 — **사용자 친화성과 안전성을 동시에 확보**한 설계
- **능동/대화형 가이드 UX**: 시스템이 먼저 안내(능동)하고, 인식 결과에 따라 추가 요청(대화형, "약을 눕혀주세요" 등)하는 다층 가이드 설계
- **Qt6 + C++ + QML 기능 단위 모듈 분리**: 폰 입력 수신 / 결과 표시 / 사용자 입력 모듈을 독립 구성 — 유지보수성·테스트 용이성 확보
- **MLOps 관점**: **GUI PC / 운용 서버 PC / 추론 PC / 학습 서버 4대 분리** 등 실무적 운영 구조 적용
- **플랫폼 모듈 구조**: 단일 기능이 아니라 **메디브릿지 플랫폼의 6개 모듈 중 핵심 모듈(알약 식별)을 1차 구현**한 뒤 모듈 2(복약 이력) + 모듈 5(통합 보고서) + 모듈 6(인증)을 함께 통합. 모듈 3(증상)·모듈 4(헬스케어)·확장 기능(음성 자동 기록·알림·가족 공유 등)으로의 **확장 로드맵을 명시한 플랫폼 설계** 경험
- **인증·복약이력·보고서**: 회원가입·로그인(bcrypt 해시·SQL 인젝션 방어), 복용 시각 분 단위 기록, 의사 상담용 통합 보고서(인쇄/PDF) 생성 — **End-to-End 사용자 가치를 만드는 백엔드 + UX 통합 설계** 경험

## 9. MVP 범위 vs 확장 범위 (모듈별)

본 프로젝트는 메디브릿지 플랫폼의 **모듈 1·2·5·6**을 MVP로 구현한다. 모듈 3·4와 추가 확장은 본 계획서 범위 외이다.

### 9.1 모듈 1 — 알약 식별 + 안전 점검 (MVP 핵심)

| 항목 | MVP (본 프로젝트) | 확장 (범위 외 / 추후 검토) |
| --- | --- | --- |
| 타깃 사용자 | 주 타깃: 고령층 / 보조 타깃: 청·장년층 | — |
| 대상 약 범위 | 국내 약 (식약처 OpenAPI 등재, 약 24,633품목) | 해외 약 (별도 설계 필요) |
| 카메라 | 안드로이드 S24 폰 카메라 (USB 직결 또는 WiFi 전송) | Basler pylon + Ring Light |
| **STT** | **폰 온디바이스 STT (Galaxy AI / `SpeechRecognizer`)** | **추론 PC Whisper fallback** |
| 알약 촬영 | 단면 촬영 + 사용자 가이드(앞뒷면 뒤집기) | 거울 / 지그재그 거치 (양면 촬영 대안) |
| DUR 위험 카테고리 | ① 병용금기 | ②~⑧ 추가 |
| 등록 방법 | 음성 인식(폰 STT) + 직접 입력 | + 단일 촬영 등록 |
| 등록 약 관리 | 추가 / 삭제(soft delete) / 전체 리셋(수동) | + 정확도 모니터링·정리 자동화 |
| 입력 채널 | 카메라 + 음성 질문 (둘 중 하나 또는 결합) | — |
| 의도 분류 (Stage 0.5) | LLM 기반 의도 분류기 (분류만, 응답 생성 X) | — |
| 능동/대화형 가이드 | TTS 능동·대화형 안내 | — |
| LLM·RAG 활용 | 등록 + 의도 분류 + 비의료 일반 안내 | 등록 LLM·RAG 정교화 (e약은요 자연어 요약 확대) |

### 9.2 모듈 2 — 복약 이력 관리 (MVP)

| 항목 | MVP | 확장 |
| --- | --- | --- |
| 복약 이력 기록 | 복용 시각(년·월·일·시·분)·약 종류·이름·개수·메모 + (선택) 식별 신뢰도·DUR 스냅샷 | **음성 발화로 자동 기록** ("타이레놀 2알 먹었어" → 폰 STT → LLM 추출 → DB 자동 저장) |
| 복약 이력 조회 | 화면 UI에서 일자별·약별·기간별 필터로 조회 | **음성 자연어 조회** ("어제 먹은 약 뭐야?" → DB 조회 + 템플릿 출력) |
