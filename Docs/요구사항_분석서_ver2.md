# 1. 문서 개요

## 1.1 목적

본 문서는 **메디브릿지(MediBridge) 플랫폼**의 기능 요구사항과 비기능 요구사항을 정의한다. 메디브릿지는 알약 식별·복약 이력·증상 기록·헬스케어 데이터 연동·통합 보고서 등 6개 모듈로 구성되는 복약·건강 통합 케어 플랫폼이며, 본 프로젝트의 MVP 범위는 **모듈 1(알약 식별 + 안전 점검) + 모듈 2(복약 이력) + 모듈 5(통합 보고서) + 모듈 6(인증)** 이다. 본 문서는 시스템을 기능 단위로 분리하여 개발·통합·검수 단계에서 팀이 합의된 명세로 활용한다.

## 1.2 적용 범위

MVP(본 프로젝트 범위)에 한정하여 명세하고, 확장 범위는 비고로 표기한다. 학생 포트폴리오 범위로 한정하되, 사업화 단계에서 확장 가능한 구조로 설계한다.

## 1.3 기능 영역 분리 원칙

> 본 절은 시스템을 **기능 단위로 분리**한 분류이다. 팀원과 영역 간의 1:1 매핑을 두지 않는다. 모든 팀원이 AI 모델링·학습·평가 작업에 공동 참여하며, 각 영역은 팀 협의로 1차 책임자만 두고 작업은 협업 중심으로 진행한다.

| 영역 | 담당 영역 | 주요 책임 |
| --- | --- | --- |
| **영역 A** | AI 추론 / Vision / Speech | YOLO26 검출, PaddleOCR 인식, OpenCV 색·모양 분석, **(확장) Whisper STT fallback**, LLM 의도 분류기, 등록·일반 안내 보조 LLM·RAG |
| **영역 B** | 운용 서버 / DB / 통신 / 캐싱 | FastAPI 백엔드, MariaDB(약 풀 + 식약처 4종 캐시), DUR 위험 템플릿, TCP/IP·REST API 통신, 인젝션 방어, 자원 모니터링·자동 재연결 |
| **영역 C** | GUI / 클라이언트 / 사용자 인터페이스 | Qt6+C+++QML GUI(기능 단위 모듈 분리), **폰(S24) 입력 수신(이미지 + STT 텍스트)**, TTS 클라이언트, 결과 표시, 등록·관리 UI, 능동/대화형 가이드 |

**공동 진행 영역 (전원 참여)**

- AI 모델링·학습·평가 — 데이터 준비, 학습 파이프라인 운영, 모델 평가는 팀 전원이 공동 진행
- 데이터셋 수집·정리 — AI Hub 5,000종 + 식약처 데이터 정제는 공동 책임
- 인터페이스 합의 — 영역 간 인터페이스(REST API, TCP/IP, DB 스키마)는 팀 협의로 확정
- 통합 테스트 — 통합 단계는 모두 참여
- 1차 제출 문서(개발계획서·개발스케줄·요구사항 분석서·순서도·디자인 목업·DB ERD·통신 프로토콜) 공동 작성 후 팀장(김윤식)이 일괄 제출

## 1.4 용어 정의

| **용어** | **정의** |
| --- | --- |
| DUR | Drug Utilization Review. 식약처가 제공하는 의약품 안전사용 정보(병용금기·중복 처방 등 8종 위험 카테고리) |
| e약은요 | 식약처 의약품개요정보 OpenAPI. 효능·복용법·주의사항·상호작용·부작용·보관법 제공 |
| 낱알식별 | 식약처 「의약품 낱알식별 표시 등에 관한 규정」(고시 제2004-85호) 근거. 모양·색·각인·제조사 정보 |
| 사전 등록(Onboarding) | 사용자가 자신이 복용 중인 약을 미리 등록하여, 식별 범위를 5,000종 → N종(예: 30종)으로 축소하는 절차 |
| Stage 0.5 | 일상 사용 시 사용자 음성 발화의 의도(약 식별/위험 점검/정보 확인/등록/복약 이력 조회/보고서 출력/기타)를 LLM이 분류만 수행하는 단계 (응답 생성 X) |
| 능동 가이드 | 시스템이 사용자에게 먼저 안내하는 TTS 멘트 (예: "카메라로 약을 비춰주세요") |
| 대화형 가이드 | 인식 결과에 따라 추가 요청을 하는 TTS 멘트 (예: "약이 서 있어요. 눕혀주세요") |
| **폰 온디바이스 STT** | **안드로이드 S24의 내장 AI(Galaxy AI / Android `SpeechRecognizer` API)로 클라이언트 측에서 음성을 텍스트로 변환하는 방식. 음성 바이너리는 서버 구간에 전송하지 않음 (v2.0 신규)** |
| 일괄 적재 | 식약처 CSV/EXCEL 또는 스마트싱크(MariaDB 자동 동기화)로 낱알식별·DUR 품목·DUR 성분을 MariaDB에 초기 적재 + 주기적(월 1회 또는 수동) 갱신 |
| lazy 캐싱 | e약은요 데이터를 사용자 요청 시점에 외부 API로 조회 후 DB에 누적 저장. 만료 정책(TTL) 없음 (v1.0의 30일 TTL 정책 폐기) |
| MVP | Minimum Viable Product. 본 프로젝트 1차 개발 범위 |

# 2. 시스템 개요

## 2.1 한 줄 컨셉

**메디브릿지** — 알약 식별·복약 이력·증상·헬스케어 데이터를 통합해 의사 상담용 보고서로 연결하는 **복약·건강 통합 케어 플랫폼**.

본 MVP는 그중 **모듈 1: 알약 식별 + 안전 점검** 을 중심으로, 모듈 2(복약 이력), 모듈 5(통합 보고서), 모듈 6(인증)을 함께 구현한다. 모듈 1은 알약 사진(여러 알 동시 촬영 가능)과 음성 질문(폰 온디바이스 STT로 텍스트 변환)을 입력으로 받아 약을 식별하고, 식약처 DUR과 결합해 병용금기·중복 처방 위험을 점검하는 한국 식약처 데이터 기반의 국내 알약 식별 도구이다.

## 2.1.1 메디브릿지 플랫폼 모듈 구조

| # | 모듈 | 본 프로젝트 (MVP) | 비고 |
| --- | --- | --- | --- |
| **1** | **알약 식별 + 안전 점검** | ✅ 핵심 | YOLO26·PaddleOCR·OpenCV·LLM·식약처 DUR. 본 문서 4·5·6장 대부분이 모듈 1 구현 명세 |
| **2** | **복약 이력 관리** | ✅ 포함 | 복용 시각·약·개수·메모. 5.11 (FR-B9), 6.10 (FR-C8) 참조 |
| **3** | 증상 / 부작용 기록 | ⚠️ 확장 | 본 MVP 미구현. 향후 모듈로 추가 예정 |
| **4** | 헬스케어 데이터 연동 | ⚠️ 확장 | 핸드폰 심박·걸음·수면 (Health Connect / HealthKit) |
| **5** | **통합 보고서** | ✅ 포함 | MVP는 약 정보 + 복약 이력 + 식약처 부작용 인용. 5.11 / 6.10 참조 |
| **6** | **사용자 계정 / 인증** | ✅ 포함 (공통 인프라) | 5.10 (FR-B8), 6.9 (FR-C7) 참조 |

### 확장 로드맵

- 음성 → 복약 이력 자동 기록 ("타이레놀 2알 먹었어" → 폰 STT → LLM 추출 → DB 저장)
- 음성 → 복약 이력 자연어 조회 ("어제 먹은 약 뭐야?" → DB 조회 + 템플릿 출력)
- 복약 알림·리마인더, 가족·간병인 공유, 약사·의료진 연계, 자유 대화 컨텍스트 유지

## 2.2 핵심 설계 원칙

- 사전 등록 + 다층 안전 메커니즘 + 2단계 추론 시스템 + 식약처 데이터 일괄 적재 + 폰 온디바이스 STT
- "진단" 도구가 아닌 "안전성 점검 도우미" — 약사·의사 상담 권유 톤 일관 유지
- 국내 알약(식약처 OpenAPI 등재, 약 24,633품목) 한정 — 해외 약은 본 프로젝트 범위 외
- 의료 안내 영역에는 LLM·RAG 모두 미사용 (환각·왜곡 방지). 비의료 영역(등록·일반 안내)에 한해 RAG 허용
- **음성 데이터는 폰에서 텍스트로 변환된 뒤에만 서버로 송신** — 대역폭·개인정보 노출 위험 최소화 (v2.0 신규)

## 2.3 시스템 구성 (PC 4대 분리 + 폰 입력 디바이스)

| **PC** | **역할** | **주요 구성** |
| --- | --- | --- |
| ① GUI PC | 사용자 클라이언트 | Qt6 + C++ + QML, **폰(S24) 입력 수신**(USB/WiFi: 이미지 + STT 텍스트), TTS 출력, 사용자 입력 |
| ② 운용 서버 PC | 비즈니스 로직 + DB | FastAPI, MariaDB(약 풀 + 식약처 4종 캐시), 위험 템플릿 생성, 인젝션 방어 |
| ③ 추론 PC | AI 추론 (GPU) | YOLO26 + PaddleOCR + OpenCV (Vision), **(확장 fallback) Whisper STT**, LLM 의도 분류기·등록 보조 |
| ④ 학습 서버 | 별도, 운용 중 비활성 | 데이터 수집·모델 학습·검증 후 추론 PC로 모델 배포(SCP) |
| **(입력 디바이스) 안드로이드 S24** | 카메라 + 마이크 + 온디바이스 STT | Galaxy AI / `SpeechRecognizer`로 음성을 텍스트 변환. 이미지·텍스트를 GUI PC로 전달 |

## 2.4 통신 구간

| **#** | **구간** | **방식** | **비고** |
| --- | --- | --- | --- |
| 1 | GUI PC ↔ 운용 서버 PC | **TCP/IP (REST API on HTTP) + 미디어/텍스트 별도 엔드포인트** | 일반 API는 REST, 이미지/STT 텍스트는 별도 엔드포인트 |
| 2 | 운용 서버 PC ↔ 추론 PC | TCP/IP (REST API on HTTP) | 추론 요청·응답. REST API 단일화 (gRPC 미사용) |
| 3 | **폰(S24) ↔ GUI PC** | **USB 또는 WiFi** | **MVP**: 안드로이드 S24 카메라 + 마이크 + 온디바이스 STT / **확장**: pylon SDK USB 직결 |
| 4 | 운용 서버 ↔ 식약처 OpenAPI | HTTPS | **e약은요 lazy 캐싱 시에만 호출** (낱알식별·DUR은 일괄 적재이므로 운용 중 호출 없음) |
| 5 | 학습 서버 → 추론 PC | SCP / 파일 전송 | 모델 배포 시에만 발생, 운용 중엔 통신 없음 |

# 3. 시스템 전반 요구사항 (공통)

## 3.1 기능 흐름 요약

- [1] 사전 등록(Onboarding): 음성 인식(폰 온디바이스 STT) / 직접 입력 / (확장) 단일 촬영. 식별 범위를 5,000종 → N종으로 축소. 추가/삭제(soft delete)/전체 리셋(수동) 지원
- [2] 일상 사용 (Stage 0.5): 사용자 음성을 폰이 텍스트로 변환 → 운용 서버 송신 → LLM이 의도만 분류 (약 식별 / 위험 점검 / 정보 확인 / 등록 요청 / 복약 이력 조회 / 보고서 출력 / 기타). 응답 생성은 하지 않음
- [3] Stage 1 (식별): 폰 카메라 → YOLO26 검출 → PaddleOCR + OpenCV (색·모양·크기) → 식약처 낱알식별 캐시 매칭 (등록 N종 풀 우선)
- [4] Stage 2 (위험 검출): 식별된 약 조합 → 식약처 DUR 캐시 조회 → 정해진 템플릿 출력 (LLM·RAG 미사용) → 화면 + TTS

## 3.2 LLM·RAG 활용 영역 정책 (필수)

| **영역** | **활용 여부** | **내용** |
| --- | --- | --- |
| 변환·인식 AI (YOLO26, PaddleOCR, **폰 온디바이스 STT**) | **✓ 사용** | 의료 정보 창작이 아닌 변환·인식 — 적극 활용 |
| 의료 안내 영역 (DUR 위험 안내, 진단성 응답) | **✗ 금지** | LLM·RAG 모두 미사용. 식약처 DUR 데이터를 정해진 템플릿으로만 출력 |
| 약 정보 등록(Onboarding) 단계 | **✓ 허용 (RAG 포함)** | 약명 추출·정규화, 모호한 약명 후보 추천, 동명·동성분 분기 질문, e약은요 자연어 요약 |
| 일상 사용 의도 분류기 (Stage 0.5) | **✓ 분류만** | 카테고리 분류만 수행. 응답 생성·의료 안내 영역 진입 ❌. JSON 스키마 강제 출력 |
| 비의료 일반 안내 보조 | **✓ 허용 (RAG 포함)** | e약은요의 비위험 정보(효능·복용법 등) 자연어 요약 |
| 외부 인터넷 출처 (블로그·논문 등) | **✗ 금지** | 약 조합 위험 정보는 식약처 DUR/e약은요만 사용. 법적·의료적 책임 소재 불분명 |

## 3.3 표현 톤 정책 (필수)

**⚠ 단정 문구 금지**

# 4. 영역 A — AI 추론 / Vision / Speech 요구사항

> 본 장의 요구사항은 주로 **모듈 1(알약 식별 + 안전 점검)** 의 추론 부분, 그리고 모듈 2/5/6에서 공통으로 활용되는 LLM 요구사항을 포함한다. **STT는 폰 온디바이스로 이전되어 영역 A의 MVP 책임에서 제외된다 (확장 fallback으로만 잔존).**

# 5. 영역 B — 운용 서버 / DB / 통신 / 캐싱 요구사항

> 본 장의 요구사항은 **모듈 1(알약 식별 + 안전 점검)** 의 비즈니스 로직 및 식약처 데이터 적재 + **모듈 2(복약 이력)** + **모듈 5(통합 보고서)** + **모듈 6(인증)** 의 서버측 요구사항을 포함한다.

**기능 범위:** 운용 서버 PC의 모든 비즈니스 로직, MariaDB 운영(사용자 약 풀 + 식약처 4종 캐시 미러링), 위험 안내 템플릿 생성, GUI PC ↔ 추론 PC 양 방향 통신, 프롬프트 인젝션 방어, 자원 모니터링 / 자동 재연결 / 로깅.

## 5.3 식약처 데이터 적재 (CSV 일괄 + lazy 캐싱)

### 5.3.1 기능 개요

식약처 데이터는 두 가지 방식으로 분리하여 적재한다.

- **일괄 적재 데이터**: 낱알식별, DUR 품목, DUR 성분 — 식별·위험 점검의 핵심 데이터로, 식약처가 제공하는 CSV/EXCEL 파일 또는 스마트싱크(MariaDB 자동 동기화 도구)로 초기 일괄 적재. 운용 중에는 외부 API 호출이 거의 발생하지 않는다.
- **lazy 캐싱 데이터**: e약은요(효능·복용법·주의사항 등) — 사용자가 등록하거나 조회한 약에 한정해, 요청 시점에 외부 API에서 받아 DB에 누적 저장. 다음 요청부터는 DB에서 반환. **만료 정책(TTL) 없음.**

### 5.3.2 기능 요구사항 (FR-B3)

| **ID** | **요구사항** | **범위** |
| --- | --- | --- |
| FR-B3-01 | 낱알식별 / DUR 품목 / DUR 성분 데이터를 식약처 CSV/EXCEL 파일 또는 스마트싱크 도구를 통해 MariaDB에 일괄 적재할 수 있어야 한다. | MVP |

# 7. 영역 간 인터페이스 종합

## 7.1 일상 사용 시퀀스 (식별 + 위험 점검)

- [폰 → C] 폰(S24)이 카메라 이미지 + (선택) 폰 온디바이스 STT 결과 텍스트를 USB/WiFi로 GUI PC에 전달
- [C → B] GUI PC가 이미지를 `POST /media/image`, STT 텍스트를 `POST /speech/utterance`로 운용 서버에 송신
- [B → A] 운용 서버가 추론 PC에 REST API로 (a) 의도 분류, (b) 알약 검출, (c) 각인·색·모양 분석을 순차/병렬 호출 (※ STT는 MVP에서 폰이 처리하므로 추론 PC 호출 없음)
- [A → B] 추론 PC가 식별 후보 + 신뢰도 + 의도 카테고리를 반환
- [B 내부] 사용자 약 풀과 결합 → 식약처 낱알식별 캐시에서 매칭 → 식별 확정 → DUR 캐시 조회 → 위험 검출 → 정해진 템플릿으로 출력 메시지 생성
- [B → C] 운용 서버가 GUI PC에 결과 메시지 전송 (신뢰도 분기 정보 포함)
- [C 내부] 화면 표시 + TTS 출력. 신뢰도에 따라 능동/대화형 가이드 추가 트리거

## 7.2 사전 등록 시퀀스

- [폰 → C] 음성 인식 등록의 경우, 폰이 STT로 변환한 텍스트를 GUI PC에 전달
- [C → B] GUI PC가 STT 텍스트를 `POST /speech/utterance` 또는 등록 전용 엔드포인트로 운용 서버에 송신
- [B → A] 운용 서버가 추론 PC로 약명 정규화 LLM 호출 (POST /onboarding/normalize)
- [A → B] 추출된 약명 후보를 반환
- [B 내부] 식약처 낱알식별 캐시에서 후보 검색 → 동명·동성분 분기 필요 시 LLM 분기 질문 생성 호출
- [B → C] 후보 + 분기 질문을 GUI PC로 전달
- [C → B] 사용자 확인 응답을 운용 서버로 송신 → 사용자 약 풀 DB에 저장

# 8. 비기능 요구사항 (전체)

## 8.1 성능

- 추론 응답 시간 — 사용자 체감 가능한 수준 이내 (구체 목표값은 통합 테스트에서 측정·확정)
- 캐시 적중 시 식약처 데이터 조회 응답 시간 최소화
- 자원 한도 내 동작 보장 — 모델 로딩/언로딩 전략 + 추론 배치 사이즈 관리
- **음성 페이로드 절감** — 폰 온디바이스 STT 채택으로 운용 서버·추론 PC 구간에 음성 바이너리 송신 없음

## 8.2 안전성 (의료)

- 의료 안내 영역에 LLM·RAG 사용 금지 — 호출 코드 자체 부재
- 단정 문구 금지 — 모든 결과에 "추정" 톤
- 외부 인터넷 출처 금지 — 식약처 데이터 외 사용 X
- 안전 케이스도 "상담 권유" 톤 유지

## 8.3 안정성 (인프라)

- 자원 모니터링 — CPU·메모리·GPU 실시간
- 자동 재연결 — 폰/카메라/통신 단절 시
- 자원 누수 방지 — 24시간+ 운용 시
- 외부 API 장애 시 캐시 fallback 동작
- 주기적 헬스체크 + 비정상 상태 자동 복구

## 8.4 보안

- 프롬프트 인젝션 방어 — 입력 검증 + 시스템 프롬프트 락 + 영역 분리 + 로그 감시
- 외부 출처 사용 금지
- **음성 원본 비저장** — 폰 STT로 텍스트만 송신되므로 음성 바이너리가 서버에 남지 않음 (개인정보 보호)
- (확장) 다중 사용자 환경 시 권한 모델 — 본인 약 정보 본인만 접근

## 8.5 유지보수성

- 기능 단위 모듈 분리 — Qt6+C+++QML 기능 단위 모듈 독립 구성
- 학습 서버와 운용 서버 분리 — 학습 부하가 운용에 영향 X
- 로깅 — DEBUG/INFO/WARN/ERROR 수준 분리
- STT 어댑터 분리 — 폰 온디바이스 → Whisper fallback 전환 가능

## 8.6 데이터 정확성

- DUR 데이터는 "식약처 데이터 그대로 인용" — 가공·요약 금지
- **캐시 정책 (v2.0 단순화)** — 낱알식별·DUR은 일괄 적재 + 주기 갱신(월 1회 또는 수동), e약은요는 lazy 캐싱(만료 정책 없음). v1.0의 TTL 30일 + ETag/Last-Modified 정책은 폐기
- 등록 약 풀은 사용자 수동 트리거로만 변경 (시스템 임의 변경 X)
